# Aside language and VM reference

[中文](aside-language.zh.md) · [Documentation](README.md) · [Engine architecture](engine-architecture.md) · [Rust host interface](aside-host.md) · [Aside creator guide](https://reelvn.com/en/docs/aside-basics)

## 1. Scope and implementation

Aside is a dynamic embedded language implemented in Rust. Reel is its first host. Authors use it for story flow, game state, custom UI, components, callbacks, asynchronous flows, extensions, and tools. The language, compiler, and VM are independent of windows, media, and stage implementations. The workspace provides `aside-vm` and `aside-compiler`. Source files use the `.aside` extension. This reference defines the current execution semantics. Each section describes the features it covers.

Some language regression cases come from Quirrel. The [fixtures](../crates/aside-compiler/tests/fixtures/quirrel/README.md) retain the original inputs, outputs, and license. This reference defines Aside syntax and execution.

Aside uses dynamic values with optional type annotations and provides functions, classes, modules, exceptions, collections, observable bindings, host waits, and execution snapshots. The script heap runs cooperatively on one thread. Threads exchange owned data and stable identities.

Parsing, semantic analysis, IR, bytecode encoding and decoding, and the VM share one execution model. Features include ordinary calls and defaults, initialized local bindings and shared captured cells, exceptions and `finally`, tuples, arrays, tables, collection spread, indexed, member, and mixed assignments, optional chains, positional spread and rest, iteration over arrays, tuples, ranges, and generators, and trailing children collection. Generic host values support stable identity, shared property tables, traced private content, and retirement. Indexed assignment saves the target location before evaluating the right-hand side. Optional chains test for null at explicit optional segments, with propagation ending at parentheses. Each rest argument receives a fresh outer array.

Source and ASB support `class` and `super`, static members, inheritance, bound methods, and execution snapshots for the same package. See the [compiler interface](../crates/aside-compiler/src/lowering/mod.rs) and [VM](../crates/aside-vm/src/lib.rs) for execution admission. Reel's host resource configuration sets the capacity for dialogue and choices.

A host can provide ambient names through `AnalysisOptions.hosts`, which defaults to an empty environment. Author module declarations, locals, and explicit `use` imports take precedence. Imports and aliases follow the ordinary module rules. Reel uses this environment to make its authoring API available by default. Standalone Aside starts without those names. The environment preserves the source and its original locations for analysis, linking, and runtime diagnostics.

Host modules may declare read-only compile-time scalar constants. Constant lookup uses the resolved declaration identity. Imported aliases retain the value and local names shadow it as usual. If a normal `if` condition is determined by these constants, literals, equality comparisons, and boolean operations, the compiler emits execution code for the selected branch. Both sides go through syntax and semantic checking. Conditions with runtime inputs retain their branch at runtime.

## 2. Syntax and evaluation order

With no ordinary arguments, `component { ... }` is equivalent to `component() { ... }`. The shorthand works for named functions, local function values, and functions obtained from a member or index. Headers such as `if`, `while`, `for`, and `match` reserve the following block for control flow. Parenthesize the entire call to include a trailing children block in a header. The shorthand uses the same call and children lowering.
A trailing children call used as a standalone statement may omit its semicolon, like a control-flow block. For example, the next component can follow `column { text("标题"); }` directly. An explicit semicolon also collects the children. A newline after a standalone children call ends that statement, so an opening parenthesis on the next line begins a new expression. In a value context, a trailing children call can still be chained. Other calls, bindings, and assignments end with semicolons.

Ordinary functions use `fn` and generators use `gen fn`. An ordinary function may `await`. The host's `spawn` starts an independent task. Bindings use `let` and `let mut`, closures use `|x| expression` or `|| { statements }`, and module imports use `use`. Ordinary statements require semicolons, with the trailing children exception described above. Aside inserts no semicolons on newlines. Functions, classes, and control-flow blocks used as statements can end at the closing brace. A block evaluates to its final expression if it has no semicolon, or to null otherwise. `return`, `break`, `continue`, and `throw` end with semicolons.

```aside
use reel::{character, narrator};

fn add(a: int, b: int = 1) -> int { a + b }

fn main() {
    let mio = character("Mio");
    mio("先别开灯。");
    narrator("雨水沿着玻璃滑落。");
}
```

Identifiers, source, comments, and text use UTF-8. Identifier rules follow the XID rules for a fixed Unicode version and allow underscores. Names compare by their exact character sequences. Comments use `//` or `/* ... */`, and block comments can nest. Double-quoted strings support escapes for backslash, double quote, `n`, `r`, `t`, `0`, and `u{hex scalar}`. Invalid scalars produce an error. `f"音量：{volume}"` is interpolated, and `{{` and `}}` denote literal braces. Triple double quotes delimit multiline text and retain newlines and indentation. The `r` prefix disables escapes and the `f` prefix enables interpolation. Each string can use at most one prefix. Arrays use `[a, b]`, objects use `{name: "Mio", [key]: value}`, and tuples use `(a, b)`. Lists allow trailing commas.

Braces enclose objects in positions that require an expression and blocks where `fn`, `if`, loops, or `try` require a block. At a statement position inside a block, `{name:`, `{name,`, `{"key":`, `{[expression]:`, and `{...` start object expressions. Thus `if flag { {accept: value} } else { {back: value} }` returns the chosen object. `{label: while/for/loop ...}` is a block, as are standalone `{}` and `{name}`. Use `{name,}` or `({name})` for a one-field object. A closure written `|| {...}` has a block body. Use `|| ({name: "Mio"})` or `|| { {name: "Mio"} }` to return an object. A `match` arm likewise treats its outer bare braces as a block whose final expression supplies the result. Use `_ => ({name: value})` or `_ => { {name: value} }` for an object result. Parenthesize unions in closure parameter types, as in `|x: (A|null)| body`. At the outer level, `|` terminates the parameter list. Headers of `if`, `while`, `for`, and `match` and the base-class expression of a `class` reserve their outer braces for control flow. Parenthesize an expression in those positions to include a trailing children call.

Shorthand fields such as `{width, height}` are equivalent to `{width: width, height: height}` and read names in the current lexical scope. They can be mixed with explicit fields and spread. Object spread uses `{...base, score: 1}` and array spread uses `[...items, last]`. Both copy entries or elements in source order while sharing their inner references. Object spread copies only own slots, leaving delegates out. Later entries replace earlier ones.

Basic control flow uses `if condition { ... } else { ... }`, `while condition { ... }`, and `for pattern in values { ... }`. An `if` used as an expression requires `else`. `loop { ... }` repeats indefinitely. `break` and `continue` target the nearest loop by default. Use a loop label such as `label: while ...` and `break label;` or `continue label;` to target an outer loop. A loop has no implicit result. Each `for` iteration creates fresh bindings, and closures retain the bindings for their iteration. `a..b` excludes the end and `a..=b` includes it. Both produce integer `Range` values with a step of one. A reversed range is empty, and iteration stops before integer overflow.

Expressions generally evaluate once from left to right. Short-circuiting, conditions, and patterns have specific rules. Assignment evaluates and saves the target object and key before evaluating the right-hand side and writing. Rebinding the original object or key name during right-hand evaluation leaves the saved location intact. Compound assignment computes the location once, then reads it, evaluates the right-hand side, computes the result, and writes it. A chain such as `a = b = value;` is a statement that resolves locations from left to right, evaluates `value` once, then writes from the innermost target out. Using assignment where a value is required, such as an arithmetic operand, an argument, or a `let` initializer, produces a diagnostic. Each destructuring target uses its own atomic preparation and commit. The chain follows ordinary side-effect rules. Effects already performed survive an evaluation error, except where a host interface declares transaction semantics.

`a..b` and `a..=b` produce lazy integer ranges and `for` consumes the iterator directly. Interpolation evaluates in source order and accepts null, bool, int, float, string, and a `CoreError` message. It reuses a chunked buffer, charges and yields by byte, and seals the validated UTF-8 data in place.

Arrays, tuples, and tables provide `len()`. Arrays also provide `append(...values)` and `pop()`. Tables provide `has_own(key)` and `get(key, default: null)`. Extracted methods retain their original receiver, and own table fields with the same name take precedence. Ordinary closures stored in a table are called according to their parameter declarations. `pop()` on an empty array throws a catchable error. `append` appends its arguments in order and returns the original array.

Consecutive `///` lines immediately above a declaration supply English Markdown documentation. A blank line or ordinary comment ends the documentation group. The compiler's `documentation::declaration` reads documentation and source ranges on demand from the lossless syntax tree for editor queries. `documentation::examples` extracts `aside` fences for API example validation. Declaration macros supply documentation for host functions and properties. [Host SDK](aside-host.md)

## 3. Values, bindings, equality, and numbers

Values include null, bool, 64-bit integers and floats, immutable UTF-8 strings, `Bytes`, tuples, arrays, tables, classes, instances, closures, weak references, and registered host values. The corresponding registered interfaces construct mutable buffers, collections, and host values.

`Bytes.len()` returns the byte count. `bytes[index]` accepts a nonnegative integer index starting at zero and yields an integer from 0 to 255. A read outside the bounds reports `OutOfBounds`. Byte data is immutable. Reads access existing storage directly and value copies continue to share that storage.

`let` fixes the name binding and allows mutation of the referenced object. `let mut` allows rebinding. Parameters have fixed bindings by default. A `mut` parameter can be rebound. Inner lexical scopes can shadow a name. Reading an undeclared or uninitialized name is an error. All closures and the original scope share the `CellId` of a mutable capture. Immutable captures may be stored by value, with referenced object identity shared. Assignment and argument passing share identity objects such as arrays, tables, and instances.

```aside
let state = {score: 0};
state.score = 1;
let mut count = 0;
let next = || { count += 1; count };
```

Scalars compare by value. Arrays, tables, instances, closures, and other identity objects compare by identity. Tuples compare recursively as described in section 5. Boolean values compare separately from numbers. Mixed int and float comparisons use exact numeric relationships, without rounding large integers to floats. `+0.0`, `-0.0`, and integer zero compare equal. NaN compares unequal to itself. Infinity and NaN are valid floating-point values. NaN bit patterns and object layout are outside observable language identity.

Conditions, `!`, `&&`, and `||` accept only booleans. Logical operators short-circuit and return booleans. `??` evaluates its right side only when the left is null. Its static result type includes the non-null types of the left and the possible right-hand types. `?.`, `?[...]`, and `?(...)` short-circuit only at a null receiver. Index and argument expressions at that segment and the remaining chain are skipped. Parentheses end propagation. A missing field on a non-null receiver or an exception from a metamethod still propagates.

`is`, `value == null`, and `value != null` narrow local names and parameters that cannot be rebound. The narrowed type applies to branches of `if` and `while`, later operands in short-circuit expressions, and closures created in that branch. `!` swaps the true and false paths. If only one side of an `if` can continue, later statements use that side's type. Leaving the path restores the declared type. Rebindable names and object fields use their declared type at each read.

Overflow in integer addition, subtraction, multiplication, negation, and division is an error, including `MIN/-1`. Integer division truncates toward zero. With a float operand, arithmetic uses 64-bit floats. `%` returns the remainder for truncating division. Division by zero, including floating-point ±0, is an error. Other float operations can produce nonfinite values, subject to stricter host property contracts. `+` accepts two numbers or two strings. String interpolation formats scalar values as text.

Editor tooling infers function results, known table fields, and array element types from bound expressions and return paths. It retains the original declaration locations for cross-module hover, completion, and go-to-definition. Explicit annotations determine runtime checks. Mutable values whose type cannot be determined remain dynamic.

`std::math` is a standard library that hosts can install. It reuses Rust's `f64` functions for trigonometry in radians, `atan2`, `sqrt`, `hypot`, `pow`, exponentials, logarithms, `abs`, `floor`, `ceil`, `round`, and conversion between radians and degrees. Calls convert integer arguments to `f64` and return a float. Unsupported argument types are reported at the call. NaN and infinity follow the floating-point rules above.

`std::math::to_int(value)` returns an integer unchanged and truncates a float toward zero before converting it. NaN, infinity, and values outside the signed 64-bit range produce a `Type` error at the call.

`std::math::min(a, b)` and `std::math::max(a, b)` return the lesser or greater argument by numeric comparison, keeping that argument's type and precision. Equal inputs return the first argument. With one NaN, the result is the other argument. With two NaNs, the result is NaN. Shaders can use both functions for scalars.

`std::math::mix(a, b, weight)` interpolates linearly and extrapolates for weights outside 0 to 1. `smoothstep(edge0, edge1, value)` uses a normalized cubic transition whose slope reverses with reversed edges. With equal edges it returns 1 for `value >= edge0` and 0 otherwise. `modulo(value, divisor)` computes `value - floor(value / divisor) * divisor`. For valid finite inputs, a nonzero result has the divisor's sign. Script arithmetic uses 64-bit floats and `modulo` returns NaN for a zero divisor or nonfinite input. Shaders use 32-bit floats, finite inputs, and nonzero divisors for `modulo`.

Shader `clamp(value, minimum, maximum)` accepts dynamic bounds. If either bound is dynamic, it computes `min(max(value, minimum), maximum)` for finite inputs. This returns `maximum` if the runtime bounds are reversed. A pair of constant bounds must be finite and ordered. Every admitted argument component must be finite. The GPU's ordinary floating-point rules handle nonfinite values produced inside the shader. Ordinary script `clamp` uses the bounds checks below.

`std::math::clamp(value, minimum, maximum)` clamps a number to a closed interval by returning the input or the applicable endpoint with its original int or float type. Mixed numbers use the precision of ordinary comparisons. Reversed or NaN endpoints produce a `Type` error. A NaN input is returned unchanged.

`std::number::format(value, precision: 2, mode: "fixed")` formats an int or float as a decimal string. Fixed precision counts decimal places from 0 through 1024. Scientific precision counts significant digits from 1 through 1024. Scientific notation uses a lowercase `e` and a decimal exponent without a leading plus sign or zero padding, for example `1.000e12`. Both modes keep the requested trailing zeros and preserve integer precision across the signed 64-bit range. Rounding is to nearest, ties to even. Floats are formatted from their actual binary values, so `2.675` with two decimal places is `2.67` and `12.25` with one is `12.2`. Negative zero keeps its sign. Nonfinite values format as `NaN`, `inf`, or `-inf`. Invalid modes, noninteger or out-of-range precision, and nonnumeric arguments produce a `Type` error at the call. Conversion writes directly to a buffer charged against the VM text allowance. The precision cap bounds each native call. Source, ASB, and `derive` share the same interface.

`std::math::curve(keys)` constructs an immutable scalar curve, and `curve.sample(time)` returns the 64-bit float at that time. `keys` is a nonempty array or tuple of `{time, value, mode: "linear", in_tangent: 0, out_tangent: 0}` records. `time` and `value` are required. All numbers and sample times must be finite. Key times may be negative and must appear in nondecreasing order. The `mode` selects the interval starting at that key. `linear` interpolates linearly, `step` holds the left value, and `cubic` runs cubic Hermite interpolation using the left key's `out_tangent` and the right key's `in_tangent` in units of value per second. Repeated times represent a jump. At that time sampling returns the last key, while the preceding interval uses the first key as its right endpoint. Beyond either end the curve holds that endpoint, and a one-key curve is constant. Interpolation can overshoot the endpoints. Intermediate calculations use 64-bit float rules.

Construction copies key values in order, reading one record per construction step. Later record edits leave copied data intact. Mutating the outer array during construction reports `ConcurrentModification`, and cancelling the native continuation releases any partial result. Construction and sampling are available during initialization and `derive`. `derive` tracks the observable inputs read during construction and argument evaluation for sampling. A curve is read-only and has no task, node owner, or playback state. Ordinary heap snapshots preserve curves and extracted sample methods. Key records accept only the five listed fields. Invalid shape, order, mode, or numbers are reported at the corresponding native call.

Bitwise operations use 64-bit two's complement. Shift counts must be between 0 and 63. `>>` is arithmetic right shift, and left shifts discard bits past the width. Integer literals support decimal, `0x`, `0o`, `0b`, and separator underscores. Values outside the integer range produce an error. The negative minimum is treated as a whole constant. Floating-point comparison, parsing, rounding, formatting, and constant folding agree with runtime behavior. Operators bind from tightest to loosest in this order. Members, indexing, calls, prefixes `await ! ~ + -`, `* / %`, `+ -`, `<< >>`, `&`, `^`, `|`, `< <= > >=` and `is`, `== !=`, `&&`, `||`, `??`, `.. / ..=`, assignment. Binary operators associate to the left, except `??` and assignment, which associate to the right. Chaining comparisons or ranges requires parentheses. `is` checks a type without conversion. Assignment supplies no value. Parser and invalid-type tests follow this order.

Explicit tuple and union contracts apply to `is`, bindings, shared captures, arguments, and returns. A tuple contract checks the length and each element's type. A union accepts any branch. The checker uses an explicit work stack whose capacity is charged at load time and charges the type DAG's upper bound on work before checking. It allocates no temporary containers. A failed assignment leaves the value unpublished.
Registered nominal host types are available to annotations and `is`. Registration declares the canonical name, version, and base types. Rust assigns this identity when constructing a host value. A type check accepts the identity and its declared bases. The editor and runtime share the registration.
`Binding` is the reference returned by `bind` and `derive`. It retains the source's read and write permissions. Reading a node property returns its current value. Constructor parameters and assignments that support bindings accept either a value or a `Binding`.

`value_of(input)` reads the current value of a `Binding` or returns an ordinary value unchanged. Binding reads use the same derived dependencies and scheduling as `input.value`.
`CellContract::type_id` is an `Option<TypeId>`. Language bindings store `Some` with an in-package type. Standalone host cells store `None` and follow their own builtin contract. A host cell placeholder therefore cannot be mistaken for a package type index.

## 4. Objects, collections, and keys

A fixed array or tuple evaluates each element once from left to right before constructing the container. A fixed table literal does the same for each key and value. It builds the table from the ordered fields only after all expressions finish. Named fields use their names as string keys. Construction errors such as unhashable keys occur at that stage. Later field expressions still run and earlier side effects are preserved. On a duplicate key, the last value wins and the first insertion position is retained. The compiler preserves evaluation of every key-value pair, including apparent static duplicates.

An array is a mutable ordered sequence indexed by nonnegative integers. An out-of-range index raises an error. Standard operations include `len`, `append`, `extend`, `insert`, `remove`, `pop`, `clear`, `slice`, `find`, `contains`, and stable `sort`. Slicing and spreading an array create a new outer sequence that shares element references.

`array<T>` declares an array's element contract. A direct array literal creates an array with that contract when its declaration, parameter, return position, or other context supplies one unambiguous expected array type. For example, write `let names: array<string> = [];`. To add a contract to the contents of an existing plain array, create a copy with `let checked: array<string> = [...names];`. All writes follow the contract, including through `array` or `any` aliases. Element contracts are distinct, and `is array<T>` checks the object's current contract. `extend`, `insert`, and `resize` commit after all checks pass. `append` writes items in order and preserves those already appended if a later item fails. Sorting and removal keep the contract. Slicing and filtering copy it to the result.

On an array or tuple, `first_where(predicate)` returns the first element for which the predicate returns true, or null. `index_where(predicate)` returns its zero-based index, or null. `any(predicate)` stops on true and returns false for an empty sequence. `all(predicate)` stops on false and returns true for an empty sequence. `count(predicate)` returns the number of matches.

`map(transform)` collects the callback results into a new array. `filter(predicate)` collects matching elements in order, retaining shared references. A tuple source also produces an array. Callbacks run in a NoWait context and predicates must return bool. Execution can be spread across budget slices. If the source changes between slices or within a callback, the method reports ConcurrentModification. The caller receives the result only after all callbacks succeed.

On an array or tuple, `find(value)` returns the zero-based index of the first element equal under `==`, or null. `contains(value)` returns whether such an element exists. Both search in order using the ordinary equality rules for numbers, text, tuples, and object identity. The search and nested comparisons follow the execution budget and share the original source. Changing array contents during the search reports ConcurrentModification. Both methods can be saved for later calls and accept a named `value:` argument. `derive` tracks reads of the source contents.

The VM's builtin collection and string declarations supply parameter names, return types, and English documentation for compiler checks, completion, hover, and go-to-definition. Calls on known array, tuple, and string types check named arguments and types. A table's own field takes precedence over a builtin method with the same name, and calls use the actual field value.

`array.sort(compare: null)` stably sorts the array in ascending order, then updates it atomically and returns it. Equal elements retain their order. By default it compares mixed int and float values with precise numeric ordering, or strings by UTF-8 byte order. NaN and incomparable types raise Type. A custom `compare(a, b)` returns a negative, zero, or positive int for less than, equal to, or greater than. It uses ordinary calls to functions, closures, bound methods, and native functions in a NoWait context. Sorting uses sliced merges, linear auxiliary space, and O(n log n) comparisons and element moves. Long string comparisons also yield between slices. If the comparator raises an exception, execution is cancelled, or the source array changes, the work copy remains private. Side effects of comparator calls are preserved. The work cursor and active comparator resume from the VM snapshot without replaying completed calls.

A table is a dynamic associative object that keeps insertion order. Dot access reads a string key, and reads inspect own slots. Assignment on a plain table inserts or replaces an own slot. Replacement preserves its position. Removing and reinserting moves it to the end. `remove` deletes an own slot.

`has_own` checks own slots. `get(key, default: null)` returns the default when the key is absent. In `derive`, a successful `has_own` records a dependency on that field, so overwriting another existing field preserves the result. A miss tracks the collection, and a later insertion, removal, or clear operation triggers a fresh lookup.

`table.get_or_insert_with(key, factory)` returns the existing value, including null. On a miss, it calls `factory()` without an external wait, then inserts and returns the result. If the factory has already populated the key, the operation uses that value. Lookup, factory execution, and insertion follow the execution budget.

`table.get(key, default: null)` uses the usual key validation and yieldable table lookup. It returns the existing value, including null, false, or 0, and uses the default only for a missing key. The default is an ordinary argument evaluated under the usual call rules. Taking the method value binds the original table, and a same-name own field takes precedence. A missing lookup on a model also records a dependency, so a later insertion can update `derive`. Invalid keys and structural changes during lookup raise the usual errors. The operation reuses the lookup budget and keeps the default in the existing call-frame roots. Suspension, cancellation, and snapshots follow the same path.

Single-key reads, writes, `has_own`, and `bind` reference lookups on plain tables, models, and host properties check only the structural version. Overwriting an existing field between slices retains its key position. The operation reads or writes the current slot at completion, including after overwrites of that field or other fields. Insertion, removal, or reordering makes an unfinished lookup report ConcurrentModification. `derive` records the dependency when the actual read occurs. Copying, spreading, and `remove` still check the full content version, while the default iterator follows the structural version.

`table.remove(key)` removes an own key and returns its previous value. The remaining keys retain their insertion order and inner objects retain their identity. A missing key raises MissingKey. Invalid keys use the normal index validation. You can save the method as a value or call it with `key:`. A same-name own field still takes precedence. A removed and reinserted key is last. The lookup, work copy, and model field-position mapping follow the VM budget. Successful commit updates both content and structural versions. Cancellation or source changes between slices leave the work copy unpublished. A VM snapshot saves any unfinished call and mapping so they can resume from the same position. See [collections.aside](../examples/collections/src/main.aside).

Hashable keys include null, bool, int, float values other than NaN, string, Bytes, and tuples whose elements are all hashable. Equal keys must have identical hashes, including int and float values that are exactly equal and positive and negative zero. Mutable objects and tuples containing them raise an error that identifies the element path.

The default array iterator records the structural version. An insertion, removal, or move causes the next advance to raise ConcurrentModification. Overwrites keep this version, and iteration sees updated values at positions it has yet to visit. Use a slice or spread to fix the outer sequence. The same rules apply to writes by other tasks while a `for` body is suspended. Snapshots preserve the container schema, order, structural version, and cursor.

## 5. Tuple value semantics

`(a,b)` is a two-element tuple, `(a,)` has one element, `()` is empty, and `(a)` groups an expression. The empty tuple is distinct from null. An ordinary function without a return value returns null. Tuple arity and order are part of the value. Element expressions run once from left to right and preserve their dynamic types without numeric promotion. Tuple slots are immutable, including through destructuring.

```aside
fn measure(node) { (node.width, node.height) }
let (width, height) = measure(view);
let items = [];
let pair = (items, items);
pair[0].append("shared");
```

A tuple is shallowly immutable. In this example, both elements retain the same array. Assignment, calls, and returns share element references. The implementation can inline a tuple or share its immutable storage. GC and snapshots keep its value structure and preserve cycles formed indirectly through mutable objects.

Tuples of the same length compare each element in order using ordinary `==`, recursively for nested tuples. Mutable containers and instances still compare by identity. Tuples with different lengths are distinct, as are tuples and arrays, and `() != null`. A tuple containing NaN may compare unequal to itself, even if its storage handle is shared. Equality uses an explicit budgeted stack with bounded Rust recursion.

A tuple is a valid key only if all its elements are recursively hashable. The hash includes length, order, and each element's hash. Internal caching of a hash for immutable contents is allowed. The cached hash has no stable identity across processes. A tuple containing an array, table, instance, closure, or NaN produces a hashing error with the offending path.

`t[i]` uses a zero-based int index and rejects negative or out-of-range values. `t.len()` returns the fixed length. `slice(range)` returns a tuple. Iteration follows element order. Reads and slices retain the original element references.

The `tuple` annotation accepts any arity and element types. Structural annotations such as `(int, string)` check exact arity and each element's type. Both annotations work with parameters, returns, bindings, and `is`. `array | tuple` accepts either type of sequence.

`let (a,b) = value` matches a tuple of the exact arity using names, nested tuples, `_`, and type annotations. Return null explicitly for an optional value or use an array when length can vary.

Multiple outputs form one tuple value. `return (a,b);` returns one value. `f(pair)` passes a single argument and `f(...pair)` spreads it into positional arguments. A tuple stays whole unless explicitly unpacked. An optimization can use multiple registers as long as dynamic calls, snapshots, exceptions, and debugging observe equivalent behavior.

### Shared collection operation rules

`slice(range)` on arrays and tuples uses nonnegative indices. Its endpoints must stay within the container boundaries, and the result keeps the container type and element references. Arrays provide `insert(index, value)`, `remove(index)`, `resize(length, value: null)`, `reverse()`, `extend(items)`, `clear()`, `top()`, and `swap(a, b)`. `insert` can append at the length. `remove` returns the removed value. `top` returns the last item and raises an out-of-bounds error on an empty array. The remaining editing methods return the source array. `extend` accepts arrays or tuples and captures only the starting elements when extending from itself. Table methods `keys()`, `values()`, and `entries()` return new arrays in own-field order. Each entry is a `(key, value)` tuple. `clear()` returns the source table.

These methods accept their declared named arguments. Binding errors happen after evaluating all arguments and before editing the container. A bulk edit prepares a private work copy within the budget and commits it in one step. An exception, cancellation, or source change leaves the work copy unpublished. A content change reports ConcurrentModification and preserves the actual source. The copy shares child objects. Commit retains the identity of the container and hands old storage to incremental GC rather than destroying it linearly. `append` and `pop` retain their item-by-item behavior.

## 6. Unicode text and mutable buffers

A string stores immutable, valid UTF-8. Equality compares the original text sequence. Length and slice methods name their units explicitly as bytes or Unicode scalar values. See the [builtin method declarations](../crates/aside-vm/src/builtin_methods.rs) for signatures and English documentation.

`byte_len()` returns the UTF-8 byte count. `scalar_count()` counts Unicode scalar values, counting each scalar in combining or ZWJ sequences separately. `slice_bytes(range)` and `slice_scalars(range)` return an immutable string for a nonnegative, zero-based range without clipping the bounds. An inverted range or invalid UTF-8 boundary raises OutOfBounds. `starts_with(prefix)` and `ends_with(suffix)` compare exact text without normalization. An empty prefix or suffix always matches. `separator.join(items)` accepts an array or tuple of strings and inserts the separator between adjacent items. An empty input returns an empty string. A non-string item raises Type without implicit formatting. All these methods support their declared named arguments.

`to_ascii_lowercase()` and `to_ascii_uppercase()` return a string, including for empty input. They convert only ASCII letters and preserve other UTF-8 bytes. The implementation reuses Rust's standard library byte-slice conversion and existing sliced text buffers. It processes bytes in linear time and charges the work and allocation budgets. It applies only ASCII case conversion.

`trim()`, `trim_start()`, and `trim_end()` remove contiguous Unicode whitespace at both ends, the beginning, and the end, respectively. Rust's `char::is_whitespace` defines whitespace. Internal whitespace, normalization, and case remain as supplied. These methods take no arguments and return a string. If there is nothing to remove, they share the original string. They locate the span across UTF-8 budget slices using the existing decoding state, with at most a linear scan. They copy the retained span once and return the empty string for whitespace-only input. The cursor and unpublished result use the normal VM frame budget, cancellation, and snapshot paths.

Counts, slices, and prefix and suffix comparisons are sliced by byte. `byte_len` takes constant time. Scalar slices locate the range in one forward scan before copying. `join` appends sequentially to one private buffer and copies each output byte once. Empty items still count toward the item budget. When the source array changes between slices, it reports ConcurrentModification. Errors and cancellation leave partial results unpublished. UTF-8 decoding and scalar iteration reuse the Rust standard library. The VM manages only chunk cursors, budgets, and roots.

`string.split(separator)` returns an array of strings, splitting on whole, nonoverlapping separator matches from left to right. It keeps empty items at the start and end and between adjacent separators. An empty separator splits on Unicode scalar boundaries, including leading and trailing empties. `string.replace(pattern, replacement)` replaces every nonoverlapping match. An empty pattern inserts the replacement at the ends and between adjacent Unicode scalars. Scanning and copying yield according to work performed, sharing linear matching logic without copying all the input first. VM roots hold temporary state for GC, cancellation, and execution snapshots.

`string.contains(pattern)` checks for a complete substring. `string.find(pattern)` returns the zero-based Unicode scalar index at the start of the first match, suitable for `slice_scalars`. A miss returns `null`. The empty pattern returns `0` and `contains("")` is `true`. Matching compares original UTF-8 bytes, including case and composition. A long input is searched in budgeted slices with matching state only for the pattern and without copying the source.

`string.strip_prefix(prefix)` and `string.strip_suffix(suffix)` match one specified prefix or suffix by UTF-8 bytes. They return the remaining string on a match and null on a miss. An empty argument shares the original string. Comparing and copying the remainder follow the existing sliced budget.

Text ranges start at zero and follow Range endpoint rules. Byte slice endpoints must fall on UTF-8 boundaries. Reel's progressive reveal uses grapheme and layout information from the text service.

## 7. Patterns and branches

Executable `match` patterns include names, `_`, literals, groups, fixed-length tuples, named fields, type tests, and OR patterns. Write `pattern is Type` for a type test and `left | right` for OR. `is` binds tighter. Parenthesize unions used as type tests, as in `value is (int|null)`. Names are unique within an arm, and both sides of OR bind the same names.

```aside
let result = match event {
    "confirm" | "click" => advance(),
    "cancel" => close_panel(),
    _ => null,
};
```

`match` evaluates its input once and tries arms in source order. A guard must return bool. The result is the value of the selected arm. Guards run in NoWait and preserve side effects that have already happened. A match with no applicable arm raises MatchError. Each entry into an arm makes fresh bindings and closures retain those values. Source and ASB use the same execution path. See [match_values](../examples/match_values/src/main.aside).

`(left, right)` matches a two-element tuple. `{score, outcome: "won"}` matches a record with exactly the two listed fields. A trailing `..` allows additional own fields, as in `{kind: "card", id, ..}`. Matching reads the listed own fields directly and skips other fields. Field order is flexible. Use `field: _` to require the field while ignoring its value. A wrong shape, missing field, or failing subpattern advances to the next candidate. Bindings and the guard begin only on a complete match. Both patterns can nest. Bindings for fields of known static type use that type.

`if let pattern = value { ... } else { ... }` uses the same matcher and evaluates the input once. A match enters the first branch with the pattern bindings. Failure follows the ordinary `if` rules and enters `else` or finishes the statement. An expression that produces a value still requires `else`. For example, `if let Menu.Load { slot } = selection { open(slot); }` handles only the load option.

A module-level `enum` declares a finite set of variants for a state or result. Read a variant with no payload directly, as in `Menu.Back`. Call a variant with a payload to supply its values. Named and positional arguments follow the ordinary evaluation order, and payload fields are typed in the declaration. `pub enum` lets other modules import the type and its variants.

```aside
enum Menu { Back, Load(slot: int), }

fn select(load: bool) -> Menu {
    if load { Menu.Load(slot: 3) } else { Menu.Back }
}

fn caption(selection: Menu) -> string {
    match selection {
        Menu.Back => "Return",
        Menu.Load { slot } => f"Load slot {slot}",
    }
}
```

An arm for a variant with a payload can unpack named fields, as in `Menu.Load { slot }`, or ignore the payload with `Menu.Load`. Named fields follow the structural matching rules for record patterns. An input of known enum type requires an exhaustive match. To cover a variant, an arm must have no guard and match all of its payload values. Dynamic inputs use the usual match failure rules.

Variant identity uses the fully qualified module, enum, and variant names. A variant without payload is saved as a persistent string. One with payload is saved as a tuple containing a named-field record. Reordering variants or declarations of named payload fields preserves existing identities. For a persistent field declared as an enum, adding or removing variants, moving or renaming the enum, or changing the payload contract changes the save contract. Payloads follow the ordinary persistent-data constraints.

`let (key, value) = entry` and `for (key, value) in entries` destructure fixed-length tuples, with nested tuple patterns, names, `_`, and type annotations. They check the shape and prepare all results before creating bindings. Wrong types or lengths raise PatternMismatch. Each `for` iteration has independent captured bindings. This uses existing Is, IndexGet, and PatternRequire instructions and shares the tuple.

`let {value: item, index} = row` and `for {key, label} in items` destructure objects by field name. They read fields in written order using ordinary string indexing. A missing field reports MissingKey. Bindings are established after all reads and nested pattern checks complete.

## 8. Functions, calls, and classes

A final `...{width, height}` in a call can compile directly to named arguments. When the fields and any other named arguments are statically visible with no duplicate names, the compiler preserves evaluation order and uses the ordinary call argument window.

Classes run with a bytecode `Class` descriptor and the shared call stack. A declaration is identified by module, name, and content version. The layout is built when the class is created, and instances store only their own field slots. Construction, field initialization, and layout setup follow the execution budget. The GC traces field values and bound-method receivers. Class calls, methods, and ordinary functions share parameter names, defaults, type checks, and effect checks.

Block-local `fn` declarations establish read-only function bindings first, allowing self and mutual recursion. Captured ordinary `let` bindings remain subject to initialization checks. An uninitialized value cannot be read as null. Named arguments work for script closures and natives with a common signature and binder. Positionals precede named arguments. `fn f(a,b=1,...rest)` creates a fresh outer array for remaining positional arguments on every call, including an empty array. A rest annotation applies to the whole array binding. For element typing, declare an explicit element contract. A known annotation incompatible with an array produces a diagnostic. A rest parameter accepts only positional arguments.

The callee, all arguments, spreads, and children are evaluated once in source order before signature binding. Duplicate names, unknown names, extra arguments, and missing arguments raise errors. Defaults run in parameter order on each invocation after all supplied arguments. They can read earlier parameters and cannot read later ones or use external waits or `yield`. A default block supplies its tail value. The lexical scope of an explicit `return` starts at an ordinary function body. A `return` inside a default gives InvalidDefault, including in conditional and short-circuit branches. Nested functions declared in defaults may return at their own function boundary. `break` and `continue` apply only to loops inside the default, and `throw` propagates through argument preparation. A `children=[]` default creates a fresh array each time.

`f(...sequence)` spreads an array or tuple into positional arguments. `f(...options)` spreads a table's own entries as named arguments, requiring string keys. The operation uses only those entries and never calls delegate or user code. `f(...positional, ...named)` forwards arguments to function values, script functions, native functions, and bound methods through the normal call syntax. A spread shallowly captures the outer entries at the spread site and shares inner references. Changes to the source during budgeted copying raise ConcurrentModification. Invalid sources, non-string keys, and copy or quota errors occur during the spread. Dynamic order errors, duplicate names, slot conflicts, missing parameters, and defaults are handled at binding, after all actual arguments finish. Positional arguments must come before named arguments, and empty spreads do not affect that ordering. A named spread can follow an explicit named argument. Merge style overrides first with `{...defaults, ...style}`. Supplying the same parameter twice in a call is an error. A trailing children block supplies the final named argument.

Classes use single inheritance. Write `class Child: Parent { ... }` for a named class and `class { ... }` or `class: Parent { ... }` for an anonymous class expression. A named declaration makes a lexical binding usable as a class value. An anonymous expression returns a new class object. Instances have declared fields. `let` is read-only and `let mut` is writable. Initialization runs per instance, from base to derived. A read-only field without an initializer must be assigned once during construction. Completion checks all required fields. An instance tracks initialized fields and has state Constructing, Ready, or Failed. Success returns a Ready instance and an exception marks it Failed. Explicitly published references retain their identity, but ordinary operations on a Failed instance report ConstructionFailed. Diagnostics and status queries remain available. Reading an uninitialized field while Constructing reports UninitializedField. Side effects that already occurred follow normal language rules. The snapshot saves construction state, the field bitmap, and execution frames. A hard owner or Region revocation or `invoke_sync` budget termination also marks unfinished construction Failed through VM cleanup. GC and snapshots trace only initialized slots. All aliases and existing bound methods read the same instance state. Calling a method checks for Failed. A constructor declares its receiver explicitly as `fn init(self, ...)`. Calling the class creates the instance and calls the nearest applicable `init`. A derived class without an `init` inherits the base constructor. With a derived `init`, only that constructor is invoked automatically. It can explicitly initialize the base with `super.init(...)`. Each base constructor can run at most once, and `super.init` does not rerun field initializers.

A method call supplies the receiver once. Taking a method value creates a bound closure that retains its receiver strongly. Plain table closures receive no automatic `self`. Ordinary functions have no inherited `this`. `super.method` looks up the method starting at the lexical base class and keeps the same receiver. A bounded weak cache may reuse live bound closures without extending the life of the receiver or declaration. Each read may instead create a new closure, and event deregistration uses a Subscription token. `static let`, `static let mut`, and `static fn` belong to the class. A `static fn` has no `self`, and a read-only static initializes once. Classes can be values and local declarations. The inheritance graph must be acyclic. Reflection of public fields and methods keeps the internal layout private.

Classes, instances, and `super` support string member indices. `object[name]` and the corresponding dot access share field types, permissions, inheritance, and receiver binding. Assignment and compound assignment evaluate the object and key once each. A non-string key raises Type and an absent member raises MissingKey. Indexed assignment uses the fixed layout and can only write declared fields. An indexed read on an observable instance records a dependency on the actual field, and `bind` fixes the chosen field at creation.

A linked native function is an ordinary function value that can be stored, passed, returned, called optionally, or given to the host's CallScript callback entry. Aside bytecode uses `FunctionKind::Native(NativeId)` with tag 3 followed by a u32 registration index. Its signature must match registration. It carries no script instructions, registers, bindings, captures, or exception regions. The source map can record the position of the value read at PC 0. Ordinary calls, host startup calls, and CallScript directly use the same NativeFrame. Full arguments are bound once. Default closures and variadic arguments share the original Cell without a forwarding script frame. aside-host seeds a native FunctionDef per contract for host method binding. The compiler reuses this definition, creating one only when it is missing and source actually reads the function as a value. The VM keeps a stable function value in the module's constant roots. MakeClosure reads it without allocating an object or requiring ALLOCATE. The mechanism introduces no author globals. A script call site takes precedence as the fault source. When the host calls the value directly, the definition's value read location is used if available.

Tables read and write own fields. Classes use declared inheritance to find fields and methods. A host extends objects with registered types, properties, and callable entries. The contract is described in section 16.

## 10. Modules, types, and reflection

`use reel::{stage,text};` imports a group, `use ui::dialogue::dialogue_view;` imports one item, and `use reel::*;` imports all public names. `as` sets an alias, `pub` controls exports, and `pub use` re-exports. Namespace imports can use `use ui::dialogue;`. The resolver distinguishes module and symbol declarations. If both share the name, use an explicit group to select the symbol. A glob import cannot silently overwrite an existing name.

The host supplies source modules and the entry point to the compiler. A Reel project uses `src` as its source root and starts `main` in `src/main.aside`. Project imports are relative to `src`, so typical code writes `use ui::dialogue;`. Its module identity is `game::ui::dialogue`. The full identity is available for explicitly qualified project paths. Every path component must be a valid identifier. Shared source copied into the project uses ordinary imports, with one module environment per actual file. `main`, `game`, `reel`, and `std` are reserved. The host registers `reel` and `std`. The entry function may be private. `use` resolves during compilation and the built package retains a fixed module set.

The compiler analyzes multiple source files through their imports and emits ordinary functions and value modules as Aside bytecode. The file provider discovers source through imports and normalizes module aliases to the fixed declaration identity. One actual source file creates one environment. Import reads and re-exports share the original cell. Module binding indices in Aside bytecode list own globals followed by imports. Validation resolves and caches the actual cell indices. The physical file is stored separately in `SourceFile.path`, and runtime faults preserve that file and the expression span.

Linking first resolves all imported function and type symbols. A type-only import participates in linking and packaging, with initialization ordered by value dependencies. Unused imports and public re-exports keep their module dependencies. The SCC condensation graph initializes in topological order, dependencies first. Modules within one SCC and otherwise independent SCCs are ordered by normalized module path, followed by evaluation of top-level expressions. Linking leaves field initialization, `extends` evaluation, and arbitrary expressions to initialization. A class can be instantiated only after it is created. An uninitialized binding read reports ModuleInitializationCycle with the actual chain. Linkable functions can refer to each other even in an import cycle. Module initialization runs without external waits.

A module instance contains import bindings and private globals for a fixed version. A session creates module environments from a fixed code set. Closures and execution frames retain their code version and bindings. Code loading and execution snapshot restoration validate these identities together.

Annotations support `any`, builtin categories, class and native names, `T|null` and other unions, fixed tuples `(T,U)`, and function signatures. Write `fn(T,U) -> R` for a function type. The arrow associates to the right, and the return type can be a union. To make the function type itself a union member, write `(fn(T) -> R)|null`. A value with a specific function signature also satisfies the unrestricted `closure` category. A function type describes positional parameter types and a return type. Calls through it check argument count, each provided value, and the result. Spread arguments use the same checks. Analysis checks compatibility of known signatures. Writes of dynamic values check callability, and calls check actual values. Function identity and captures are preserved. Defaults and rest parameters can implement corresponding positional calls. A bound method hides its receiver. Waiting and cancellation follow ordinary calls. `()` is the empty tuple type. Parenthesizing one type groups it, and including a comma creates a tuple type. Annotations leave dynamic storage intact. When possible the compiler diagnoses errors statically, otherwise runtime checks apply at argument entry, return, or assignment to a declared binding. Plain `array` and `table` annotations constrain the container category and retain dynamic elements.

`{node: Node, caption: TextNode}` describes a table with those own fields. Field names and types must agree, with arbitrary order. Its value retains ordinary table identity, so it can be destructured, passed, and composed. Accessing named fields through the structural type checks their types. A later type check also sees any mutations made through other aliases.

`{asset: string, hover_sound?: string}` allows the `hover_sound` field to be absent. If present, its value must be a string. To allow explicit null, use `hover_sound?: string | null`. Reading a missing optional field returns `null`. `has_own` distinguishes a missing key from an explicit `null`. `.get(key, default: value)` can still supply a default. Assigning an optional field can create that key, subject to its declared type. Record types accept only declared keys. Record patterns match actual presence. Saves retain both presence and value and validate the same type contract.

Use a module-level declaration such as `type Context = {scene: Node, caption: TextNode};` to name an existing type. Aliases support annotations, `is`, and forward references. Export with `pub type`. Other modules can import, rename, and re-export aliases through `use` and `pub use`. Aliases expand at compile time with identical type checking, save contracts, and bytecode representations. They provide no values or constructors. Alias cycles report their source positions. `type` remains usable as a name outside declarations.

A string literal can serve as a type. For example, `fn menu() -> "back" | "title"` limits its result to those two values. An incompatible literal reports an error at the expression. Dynamic values follow ordinary type checks for arguments, bindings, and returns. Literal types also work with `is` and compare decoded string contents.

A direct lambda can infer its unannotated parameters and result from one expected Callable type before analysis of its body. This inference applies to call arguments, typed `let`, assignments, and returns. An optional Callable supplies its function signature. Explicit parameter annotations are preserved and checked for compatibility. Ambiguous unions and spread arguments that cannot be matched statically use the dynamic rules. Callable signatures leave wait effects to the call context, including NoWait.

Scripts check types with `is`. Host declarations supply the compiler and editor with one set of registered types, fields, parameters, defaults, and effects.

## 11. Children and observable bindings

A trailing children block is general call syntax. It immediately evaluates an array argument named `children`. The block runs once at the call site. A standalone expression statement producing a Node adds it in order, even with a semicolon. A final Node is collected once. Null is skipped and any other value produces an error. Initializers and assignments do not collect nodes. `if`, `for`, `while`, `match`, and ordinary statement blocks inherit collection lexically. The control flow expression as a whole does not collect the final value again. A nested trailing block has its own collector, and a called function does not inherit the collector. Use one of an explicit `children` argument or a trailing block. Pass event callbacks by name.

At a collection site, `...items;` adds array or tuple elements to the current children in order. It evaluates the operand once, validates each element under the ordinary child rules, and skips null. The spread uses existing budget slices and concurrent modification checks.

A host can declare `must_use_result` for an external symbol. Semantic analysis checks statically recognized results. An ordinary statement discarding such a result emits `ASS016` at the constructor call. Reel's stage node constructors use this declaration, so `fn heading() { text("标题"); }` prompts the author to return or use the node. Use the final value `text("标题")` or `return text("标题");`. Returns, bindings, arguments, and children collection use the result. `let _ = text("标题");` deliberately discards it. `text("标题");` inside children still collects the node. Ordinary function bodies, modules, and scene entry points follow their block-value rules. Statements inside a value subexpression are checked independently. For example, `let x = if true { text("标题"); 1 } else { 0 };` within children still reports the discarded result.

The check uses external declaration identity across imports, re-exports, and simple immutable binding aliases. Author functions, mutable function values, dynamic members, and indexed calls follow their existing dynamic contracts. An optional component may explicitly return null, and ordinary side-effecting calls can be statements.

```aside
fn panel(title, children = []) {
    column(gap: 12) {
        text(title);
        ...children;
    }
}
let view = panel("声音") {
    slider(value: bind(settings.music), min: 0, max: 1);
    text(value: derive(|| f"音量：{settings.music}"));
};
```

Children construction runs without external waits. BudgetYield can save temporary construction frames. Nodes are returned unattached. The host validates single-parent ownership and transactional attachment.

The compiler recognizes `bind(model.volume)` as a reference to an observable property location and produces a Read or ReadWrite PropertyRef. The object and key are evaluated once and the reference retains that location. The host registers a stable property identity, reads, optional writes, and versions. Ordinary table fields outside a model, temporary values, and expressions such as `a+b` cannot be bound. Reel provides observable application state through `model({...})` and observable collections. Create a new reference to select a different location.

When a derived value or component reads another derived value, the read first finishes any pending recomputation of its source. Range checks and indexing can compose through multiple `derive` calls. A conditional branch reads newly encountered sources from the current batch. An ordinary synchronous script segment still schedules derivations together after it finishes. Refresh uses the same VM task, native continuation, and dependency capture. Cancellation, faults, and restoration during a read preserve its position. Derivation uses the task budget, and a dependency cycle raises an error.

For host properties, `bind(node.x)` and `bind(node[key])` fix the receiver and key and retain the location's read and write rights. A node constructor argument or property assignment that accepts a reference establishes a connection. Subsequent writes of ordinary values pass through to the source. `unbind(bind(node.x))` disconnects that location and returns and retains its current value. Cycles, unobservable locations, invalid sources, and writes to read-only locations produce errors. Updates validate all proposed affected values before committing them together. A rejected update preserves the previous values and connections. Explicit source retirement freezes existing connections at the last valid value and disconnects them. Further use of a reference to the source reports that it was destroyed. A source is destroyed only by explicit retirement, and GC retains referenced sources. Animation acquires write access to the final source. Rebinding or disconnecting stops activities that depend on the previous connection. Binding reads the source's current value and lets its own activities continue.

Observed model tables retain stable field identities in live insertion order. Within one property generation, field IDs increase and are never reused; clearing the table starts a new generation. Deleting a field releases its position and property metadata and invalidates references to that field. Surviving bindings, versions and activity claims keep their identities. Position lookup and removal storage depend on the live table size, including after repeated insertion and deletion.

The host can wrap an ordinary data graph in observable state. The host defines data copying, application types, and which resources are excluded. For Reel models, controls, and the Reading lifecycle, see [engine architecture](engine-architecture.md#stage-layout-and-text).

`derive(|| expression)` creates a read-only DerivedBinding and records actual observable reads. A changed version triggers recomputation and replacement of conditional dependencies. Derivation cannot modify external objects or observable state, start an activity, or wait. Called natives must be DerivedSafe, and the restriction follows nested calls. Temporary internal allocation and writes are allowed when they do not escape as external mutable effects. Ordinary captures preserve shared-value semantics, with reactivity only for observable reads. Cycles raise errors. Replacement and destruction unsubscribe. Removing the last property consumer also unsubscribes unconsumed upstream derivations. Rebinding a retained reference resumes updates without affecting shared consumers. A value frozen by host input retirement cannot resume. Writable controls require a writable source. The host handles notification and transaction commits.

A derived result is a read-only property reference available through `binding.value` or as an input to another derivation. Dependency changes coalesce at the commit after a synchronous script segment, stabilizing before the next stage publication or application task without a per-frame binding scan. Changing private host payloads retains the GC write barrier and leaves public property dependencies intact. Publishing a public property invalidates its corresponding dependency. Reel's continuous clocks and dialogue reveal finish the current derivation batch before publishing the next sample. Service getters within derivation use a batch projection initialized at first creation. Explicit author commands still publish actual changes immediately. The first computation runs on the original stack. Subsequent computations preserve the closure's source position. A failed computation retains the last valid projection and reports a script fault.

Dependency capture retains a strong reference to the source and its stable generational identity. The actual capacity counts toward the heap budget. Commit, cancellation, collection, and restoration maintain the same dependency graph. Before rendering, the host verifies relevant derivations and their upstream sources. Synchronous lookup, subscription, and unsubscription work scales with the actual graph. See [reactive](../crates/aside-vm/src/heap/reactive.rs) for traversal and caching.

## 12. Tasks, Awaitables, and cancellation

The executor provides ordinary tasks, host Awaitables, hard revocation, and resumable waits. Reel combines these primitives through completion and spawn.

An ordinary `fn` runs on the current Task's resumable call stack and can await. Reel runs the entry point and UI callbacks in tasks with an explicit OwnerId. A suspending native such as `say` can suspend an ordinary chain of helpers. A function returning an awaitable returns that object for the caller to await explicitly. A dynamic attempt to wait externally outside a task or inside a restricted boundary raises an error.

`narrator(...)`, character dialogue, `Speech.wait()`, and `choose(...)` complete their waits within the current story task and provide the result of the call expression. `stage.transition(...)` returns the result of `change` after the transition completes. `action.run(...)`, `stage.presented()`, and `saves.save(...)` return awaitable activities or requests so the caller decides when to `await`. A statically proven non-awaitable operand reports a diagnostic at `await`, and the editor can remove the keyword.

`spawn(work, owner: null)` starts zero-argument script work in Reel and returns an awaitable, cancellable host task. Node ownership and cancellation follow the engine's author activity contract. This uses the ordinary call stack. VM task slots grow with the number of concurrent active tasks and are reused. The default has no fixed task-count quota. A host can set `VmLimits.max_tasks`. At admission, each logical task checks contiguous execution space, whether reusing a finished slot or recomputing a derivation. FrameSlots checks for a contiguous free span, compacts or grows as needed, and preserves root identities. Overlapping old and new buffers are charged to the heap and obey host capacity limits.

`await` accepts an Awaitable. Other values raise NotAwaitable (core code 24) at the keyword, with a hint that ordinary calls already wait for their return values. That fault uses the existing fault and source stack and leaves allocation and bytecode instruction format unchanged. Reel's Task, Activity, Completion, SaveRequest, LoadRequest, and DeleteRequest implement the protocol directly, so write `await activity` or `await request`. Even a completed value resumes on the next scheduling step. A single completion delivers to all waiters in registration order. Faults establish a new consumer fault at `await`. Its origin and stack identify the awaiting call chain, while `AwaitedFault.source` retains the full producer fault and its original location. An Activity's Stopped state is an ordinary result and Cancelled raises cancellation. An Awaitable must explicitly define wait registration, unsubscription, result state, and restoration.

The VM binds a trusted host Awaitable to a single-parameter native admitted by the current package. The parameter is the object itself, typed any, with no default or rest. The native declares WAIT. The binding is outside script-writable fields. Await checks dynamic NoWait and effect restrictions, then enters the existing NativeFrame. The first HostCall is a scheduling boundary. Even Ready does not run script inside the response call. Pending, Continue, CallScript, generational WaitId, roots, and cancellation reuse the ordinary native call path. Each await forwarding a producer fault creates a separate consumer envelope, preserves the original value and error code, and records the source fault and activation through AwaitedFault. The catch cause is preserved too. The host maintains subscriptions in registration order and uses `wait_is_pending` after cancellation or completion. Unsubscribing one consumer leaves the shared producer running. A completion after task or owner revocation cannot be delivered. The restoration descriptor includes the native identity and version for the current host package.

Cancelling a host task or retiring its owner hard-stops the task without running its script `finally` blocks. The host idempotently releases owned subscriptions, resources, and activities. Cancellation preserves earlier shared-state writes. Required cleanup relies on Owner or ResourceToken. A close operation that waits must be explicitly awaited while the owner remains valid.

A host one-shot result can implement the same Awaitable protocol. Its declaration specifies the producer owner, single terminal result, repeat waits, and subscription cancellation. Cancelling a waiter only removes that waiter's subscription.

Inside Rust hosts, weak registrations use `Heap::peek_weakref` to inspect an object in a transaction that performs no GC, without retaining the object for the current marking cycle. Use `upgrade_weakref` to retain a value across transactions. Property subscriptions use the same narrow interface.

## 13. Iteration

`for` accepts arrays, tuples, integer ranges, and generators. Captured locals receive a new binding per iteration. `for index, item in values` also binds the zero-based int index. The index position takes a name or `_`, and the second position accepts an ordinary loop pattern. The index increments on each element read and continues in order after `continue`. Source evaluation, iteration, errors, and cleanup follow ordinary `for` with no intermediate array or per-item index tuple. Shader loops retain one binding.

A call to `gen fn` binds arguments and evaluates defaults using ordinary function rules, then returns a generator. Its body starts on the first advance. `yield value` delivers one value and saves local state. Advancing resumes there, and the `yield` expression evaluates to `null`. A `-> T` annotation constrains the final return value. The yielded item's type is inferred from `yield`. The callable return type of the function is `generator`. Instance methods may use `gen fn`, while constructors named `init` use ordinary `fn`.

`next()` returns `(done, value)`. A yield returns `(false, value)`, the first termination returns `(true, final_value)`, and subsequent calls return `(true, null)`. `for` consumes only yielded values and closes the iterator on completion, `break`, `return`, or exception. `close()` returns `null`, runs entered `finally` blocks, and closes the generator. An unstarted or exhausted generator closes immediately.

A generator resumes under the caller's execution budget, effects, and wait permissions. Its body and callees are NoWait. Advancing or closing a running generator raises InvalidState. An exception escaping the body closes the generator and propagates at the call site. GC and hard task cancellation release its state. Explicit close runs `finally` using ordinary exception cleanup. Suspended state, captures, and fault context use the same GC and snapshot system.

## 14. Exceptions, exits, and resources

`try {...} catch error {...} finally {...}` requires at least one of `catch` and `finally`. `throw` can raise a script value. The runtime stores its original value, stable code, source location, and stack in an ErrorEnvelope. `catch` reads the original value, and `std::core::error_info()` provides the fault details. `throw;` rethrows the current envelope only from `catch` and retains its stack. `throw value;` records this throw's location and cause.

Leaving a `try` through normal completion, `return`, `break`, `continue`, or exception runs `finally` first. A `finally` block cannot await, yield, return, or jump out of its own boundary, but may yield for the execution budget. The lexical restriction covers conditional and short-circuit branches. Nested functions are analyzed at their own boundary and inherit the caller's constraints at invocation. Ordinary helpers may return synchronously, and an actual external wait is checked against the effective NoWait restriction. A fault thrown in `finally` replaces the pending result and keeps the previous result or exception as its cause. The exception value, pending return value, and unwind location are resumable frame state.

Resource close and dispose must be idempotent with an inspectable terminal state. Files, cursors, subscriptions, and native resources use explicit tokens and owners. GC does not run user finalizers. Lower-level host release is also budgeted and queued. Since hard stops may skip script cleanup, underlying resource release must be independent. Application state that must recover from a hard stop uses host transactions or scope restoration records. Native crashes and internal invariant violations remain host failures.

A host can use `finish_host_callback(task, frame, value)` to end an active native callback region. It uses the same sliced frame-retirement path as cancellation, skips script `finally` in the region, and delivers CallbackReturned with the original value at the boundary. The outer task continues. The return value occupies the native frame's existing result root and is retained by GC and snapshots. Reel's `scope.finish(value)` uses this protocol to return a page or interaction result.

Synchronous host reentry, defaults, module initialization, constructors, derivation, `finally`, and children run without external waits. Static checks handle cases that can be proven. Dynamic calls remain checked. These boundaries may still suspend for budgeting, with the separate hard limit of `invoke_sync` described in the next section.

## 15. VM and resumable host calls

A standard zero-argument derived expression proven at admission runs in an ordinary script frame and enters the same host commit continuation at its tail. The VM uses explicit call frames, shared code and constants, interned symbols, reusable argument storage, and resumable intermediate state. The default Value is a 16-byte tagged value with a 64-bit payload. It keeps full int64 and float64 values inline and accesses heap objects with full generational handles. `run_slice` accepts instruction, allocation, and clock-check allowances and returns Returned, BudgetYield, HostCall, Waiting, Fault, or ResourceBlocked. ResourceBlocked means the hard capacity for building a complete fault record is unavailable. Section 23 defines its retention, restoration, and cancellation. BudgetYield preserves language results, and all temporary roots and continuation positions live in VM state. HostCall includes a stable function symbol, signature version, TaskId, OwnerId, source position, and borrowed argument view. Host responses are `Ready(value)`, `Pending(wait_descriptor)`, `CallScript{callee,args,continuation}`, `Continue{continuation}`, `Error(NewFault)`, and `ForwardFault(fault_id)`. Error creates a fault, and ForwardFault propagates a retained complete fault as defined in section 23.

Pending exits the native call stack before saving the operation descriptor, wait identity, return slot, and successor PC. Completion resumes only the operation's successor phase. Calls with effects that already happened are not replayed. Native asynchronous algorithms use sliced state machines or background tasks with owned data. Rust futures and stack addresses serve no role in a persistent continuation.

CallScript lets native algorithms call suspending script. The host exits the Rust stack and keeps its versioned continuation in an explicit native frame. The VM pushes a callback frame in the same Task with the same owner and effect context. On script return or throw, it resumes the continuation with `ScriptExit::Returned` or `ScriptExit::Fault`. The continuation can respond with Ready, Pending, CallScript, Continue, Error, or ForwardFault. The callee module version, arguments, algorithm phase, temporary objects, and return target are traced and saved. The original native entry runs once. Pending in the callback suspends the whole task stack.

Continue saves a versioned native algorithm state and resumes it in the same Task on the next budget slice. It needs no WaitId or external wait and does not repeat the entry call. It supports sliced encoding, hashing, and copying without script callbacks, including in restricted contexts that allow BudgetYield. The snapshot includes native frame roots and cursors.

CallScript inherits the original permissions and restrictions. A synchronous sort comparator cannot wait, and a restricted derivation cannot write external state. A host operation that uses an ordinary suspending callback declares it in its signature. The host adapter idempotently cancels and releases native frames. A script fault unhandled by the continuation propagates along the original call chain. Continuations are verified against the current package and the v1 snapshot schema.

A native continuation identifies its callback cancellation barrier by TaskId and native FrameId. After host cancellation, the VM releases inner frames under the budget and resumes the original continuation with CallbackCancelled. The outer task and its exception handling remain valid. Snapshots retain unfinished cleanup boundaries. Reel can add an owner condition while retaining the task's primary owner. `scope(owner: node, body: callback)` uses this protocol. If the node retires first, the region alone is revoked, its wait is cancelled, and callback frames are discarded up to the barrier. Inner script catch and finally cannot intercept revocation. The native adapter idempotently releases region resources, then delivers ScopeCancelled at the original call site outside the barrier. A surviving Task can continue. Revoking its primary owner hard-stops all regions. The snapshot includes the hierarchy, cancellation conditions, temporary resources, and barrier frame. The innermost active scope supplies the default resource owner, otherwise the primary owner applies. Spawned tasks and activities without an explicit owner use the default. An explicit owner transfers the lifetime.

`invoke_sync` is limited to bounded synchronous reentry that cannot retain the native stack. It inherits the remaining instruction and allocation allowances and deadline from the outermost synchronous call. A nested call can only tighten these limits and consumes their shared allowances. The whole call finishes at this boundary with Returned, Error, or an explicit synchronous control failure. Exhausting the budget terminates the nested call with NonResumableBudgetExceeded to the native. Script catch and finally cannot intercept or extend that exit. Earlier side effects remain. A native that uses this path must handle failure and release all borrows. Variable-length or suspending callbacks use CallScript. Repeated `invoke_sync` calls remain subject to the cumulative budget.

## 17. Budgets, collection, and sliced algorithms

Budgets count instructions, container elements, comparison and hash work, copied bytes, collected edges, and allocated bytes. The starting configuration checks for yield every 256 work units, with the actual target adjusted using tail-latency measurements. Native primitives must be bounded. Long strings, Unicode work, tuple equality and hashing, patterns, sorting, parsing, and copying use resumable continuations or strict input bounds. Work and allocation belong to the call budget.

Total string length is independent of the allowance for one copy. Bytecode constants load in storage blocks. Concatenation keeps construction state in its frame and copies in chunks within the work and allocation allowances. Budget exhaustion yields. A completed result is published once as an immutable string, with intermediate buffers rooted and cleaned up through exception or cancellation paths. Each chunk and temporary buffer still counts toward real heap usage. The host's chunk size for a read or write places no cap on total string length.

A sliced operation defines when intermediate state becomes visible. Sort prepares a work copy and tracks the complete source content version. If a comparator or another task changes any source position during preparation, commit reports ConcurrentModification and preserves the current source. A comparator must provide a stable, consistent order. The runtime can report detected violations while preserving container and memory safety. Success commits once and failure leaves the copy unpublished. Other tasks can run during BudgetYield. The work copy, cursor, version, and callback state are rooted and saved. Completed callbacks are never replayed on restore. Other operations with atomic results follow the same prepare and commit model.

Object identity reuses pinned slotmap 1.1.1 with a dedicated HeapKey type and full opaque 64-bit keys. The identity map stores entity positions and slot generations. Entities occupy compact pages. A removal during sweep moves at most one entity and releases at most one empty tail page. Updating a position preserves all values and root handles. Objects share those pages without individual boxes. The identity map retains generations for invalidated keys, while entity pages can be released as live objects shrink. Handles are valid only in their heap. Long-lived host references register a root handle with HeapId and SessionEpoch. Snapshots use independent object numbers and allocate new handles during restoration. Ordinary handle passing round-trips the full u64 KeyData.

A host can reuse a table read view during one shared heap borrow, amortizing identity and kind validation over consecutive field reads. The view reads chunked storage in original entry order and retains property proposal and boundary-error semantics. The heap borrow bounds its lifetime.

The script object graph uses a single-threaded incremental tri-color mark-and-sweep collector with stable integer handles. Tracing accounts for Value copies and strong heap edges without per-copy reference counting. slotmap provides slot reuse and generation validation. Aside implements entity pages, root scanning, edge cursors, write barriers, weak references, and sweep state. Existing edge and payload-byte allowances apply. Removing an entity moves at most one object and can release one 32-object page. GC queues reserve live-set capacity before admitting an object. [gc-arena](https://github.com/kyren/gc-arena) informs the algorithm and represents managed fields through its Gc interface.

External roots include live task frames, active sessions, the currently published ModuleSet environment, pending deliveries, native continuations, and host root handles. Sliced work copies and callback state are roots too. Fields, cells, elements, and closure captures are strong heap edges. Old module caches are weak indices. Allocation tables and GC work queues serve as bookkeeping. Truly immutable code or resources can use Rust Rc or Arc independently of script reachability.

Package loading reserves ModuleSet constants, symbols, native values, and globals from actual counts. `VmLimits.slots` declares the execution working set. Module roots add capacity to the same root pool at load time, while frames and continuations use their operation allowances. Both share GC scanning and heap accounting. Module size leaves the configured execution working set available.

The default HeapLimits has `max_bytes = u64::MAX`. A host can set an isolation budget. Usage and peak tracking still apply, and real allocation failures remain errors. Slice work and allocation budgets determine when execution yields. Heap and resource allowances determine content capacity.

Object identity storage, host roots, and root-range descriptors grow geometrically with demand. Default count limits are the representable range of generational handles. Configured maxima do not preallocate capacity at startup. Object admission prepares GC, release, and reactive queue capacity for the live set, allowing barriers and collection steps to run without allocation. Root-range growth extends FrameSlots mappings and preserves tokens and scan cursors. Old and new storage count during overlap. A failed allocation leaves the object or root unpublished, and any reusable capacity already acquired stays charged. Hosts may tighten the count and byte limits.

GC steps run at VM safe points. During marking, the insertion barrier marks a new strong edge target before a write or root publication becomes visible. Initial strong edges and weak reference upgrades use the same path. Root scans keep a persistent cursor, and even previously scanned roots use the barrier when updated. Large containers retain edge cursors. Insertion, removal, or reordering must correct the cursor or mark unvisited edges that moved. Once roots, gray entries, and barrier work are complete, weak determination and sweep begin at the same safe point. From weak determination through sweep completion, a weak reference can upgrade only to a confirmed live or newly allocated object. This transition is the shared liveness cutoff, beyond a simple generation check. New allocations are live for this cycle and enter the next cycle's scan.

An object without strong edges to visit is marked live when first found. When marking a container, a single lookup can scan a contiguous value segment and enqueue references in original order. Each inspected value still counts toward the edge allowance. Later writes use the insertion barrier, and replacing a container still scans any transferred edges. Weak references use their own queue.

The host starts automatic collection under allocation pressure. The heap accrues new object and payload-byte counts, then sets the next threshold from the live set at the last completed collection. By default the object threshold is the larger of 256 and half the live object count, and the payload threshold is the larger of 64 KiB and half the live payload. Reaching either threshold requests collection. Explicit allowances can trigger collection earlier. The object threshold is capped by half the remaining slots and half the object entities that fit in remaining bytes. The payload threshold is capped at half the remaining bytes. Both have a minimum of one, so small objects without payloads can request collection before filling the byte allowance with entities. Starting collection spends existing allocation debt. New allocations during the cycle accrue toward the next request and survive completion. Clearing a nonempty collection requests a subsequent cycle, retaining requests made during an active cycle so that previously marked old values can be collected. Explicit `begin_collection` and resource-blocked collection do not use automatic thresholds. Checking and requesting take constant time. Actual collection uses the same root provider, work and byte budgets, and incremental release, with no additional script parameters or snapshot state.

Roots, strong edges, weak references, and sweep have independent work allowances. Sweep uses a bounded allocation-key queue, recording the number of entries for its cycle. It inspects entries in slices and requeues live objects. New objects wait for a later cycle. Queue entries map to individual object identities to avoid double release. An object is logically invalidated before releasing its payload within the work and byte budgets. Values within a container are released together with their storage block, returning its memory allowance after release. Buffer allocation and release record the longest indivisible time. Marking queues, cursors, pending release bytes, and retired slots count toward heap capacity. Insufficient enqueue capacity is handled before publication by performing maintenance or returning a resource error, preserving the barrier. An Owner explicitly revokes device resources, and GC releases only the underlying owned data. Collection timing is independent of application determinism.

The full slotmap generation can still wrap. When removing a slot at generation exhaustion, the wrapper keeps it Retired, rejects access, and retains it through bulk cleanup. In the pinned version, the occupied generation limit is `0xffffffff`, allowing at most 2^31 lifetimes for one slot. Generation field interpretation belongs to the dependency adapter and requires a source review and dedicated cases on upgrade. Ordinary handles retain full round-trip behavior. Retired slots count toward capacity independently of live objects.

Authors can read and navigate the view, and runtime calls still enter the host implementation. In generated declarations, `name?: type` marks an omittable native parameter without a replacement default. A provided value must satisfy its type.

Semantic coloring uses the same analysis to distinguish variables, parameters, functions, types, namespaces, and members. It reports full-document name ranges through standard LSP tokens and modifiers. Editor themes determine colors. Hover and definitions locate actual names, and imports use their declaration identity, type, and documentation. Completion includes keywords valid at the current syntax position, including in unfinished declarations. Member positions offer the receiver's members. String bodies and comments retain their own editing contexts.

Module prefixes in imports support hover and go-to-definition. Host modules open generated declarations from the same source, source modules open their actual files, and directory prefixes open a navigable read-only index of directly discovered modules. Completion in blank or unfinished `use` statements uses the same discovery.

The document outline lists module functions, classes, bindings, and class members from the current syntax tree. Outline and parser quick fixes use unsaved buffers without waiting for project analysis. Edits from quick fixes apply to the current document version.

Find references uses compiler-bound symbol identities. Lexical binding searches stay within their document. For a public declaration, the language server examines the current import graph and the `main.aside` graph for the same project. It follows direct imports, aliases, re-exports, and namespace access. Open buffers override disk content.

Formatting uses the lossless syntax printer in aside-compiler. `format(&str)` parses before formatting and `format_parsed(&Parse)` uses an existing parse. Syntactically valid files can be formatted independently of name and host resolution. Syntax errors return the original diagnostics. The printer uses four spaces and targets 100 characters. Short calls fit on one line, long calls pack parameters onto continuation lines, and long member chains break by operation. Code and children blocks indent by syntax structure. Line breaks preserve statement and postfix parse relationships. String, numeric, and comment contents and non-whitespace token order stay as written. Documentation comments stay with their declarations. Output uses LF, with one final LF for nonempty files and an empty string for whitespace-only files. Formatting is idempotent.

Diagnostics include a stable code, severity, module version, primary and related spans, the call stack, and optional fixes. They preserve UTF-8 byte ranges and display lines and columns, including Chinese text. Dynamic call diagnostics identify the signature and arguments. Await and native continuations identify the wait and original fault sites. Human-readable and structured output omit internal addresses and Rust panics. Errors cover names, types, arguments, patterns, read-only writes, waiting and effect restrictions, invalid handles, resource allowances, missing code and restoration data, and invalid packages.

## 22. Bytecode and executor contracts

The public format lives in [aside-vm::bytecode](../crates/aside-vm/src/bytecode/FORMAT.md) and covers program data, verification, and disassembly. aside-compiler depends on the format, which is independent of Rowan, the parser, and Reel. These are the contracts shared by compiled output and the executor.

**Programs and verification**

BytecodePackage contains format, language, and host ABI versions, a content version, symbols, constants, modules, functions, capabilities, and source maps. ModuleDef contains the normalized path, fixed imports and exports, global bindings, and initialization entry. FunctionDef contains the Plain, Async, Generator, or Native kind, common Signature, capture layout, register count, code, and exception and cleanup regions. Generator uses a deferred body and Yield. The Async encoding is reserved until lowering and execution admission support it. Signature contains parameter names, order, types, mutability, defaults, rest, the return contract, and effects. ParameterDefault distinguishes Constant(ConstId) and Function(FunctionId). A literal references the constant pool directly. An expression entry inherits lexical captures and the ModuleInstance from the callee closure's definition and receives earlier parameters. Defaults are evaluated only when the argument is omitted. Capture analysis includes default expressions, with fresh array and table construction each time.

Script and natives share constant materialization and parameter type checks. Constant defaults reuse immutable values. Sliced aggregate constant creation, temporary rooting, cancellation, and restoration use ordinary constant loading. A constant default needs no function frame or copy of preceding parameters.

Each invocation establishes its own bindings in parameter order. Earlier parameters are initialized before a later default expression starts. Reads, writes, and closures in a default expression share its lexical parameter bindings with the function body. Parameters that need shared mutable identity get Cells here, reused by the body. Capture analysis and lowering account for both default expressions and the body. An initialized read-only prefix can pass by value when identity is irrelevant. All supplied arguments still evaluate in source order before parameter binding.

The parameter's default descriptor selects a default function. For an expression result or block tail value, the compiler emits a Return that ends that default entry. Explicit source `return` remains restricted by the default lexical boundary. Only the VM's internal default-prefix path passes earlier parameter Cell identities. Ordinary CallTarget and Arguments always carry author values and create fresh call bindings. Calling that default FunctionDef as an ordinary function follows ordinary rules too. The verifier permits Parameter(i) in Value(Reg(i)) or Cell(Reg(i)). It checks each pair of prefix names, types, mutabilities, storage layouts, and capture layouts in the callee and its default entry. The internal prefix path checks actual Cell initialization, contents, and contracts. The handle stays internal. The default entry and body share current invocation bindings, while definition-site captures still come from the callee closure's lexical environment.

Script and natives require a Cell for each mutable parameter in any later default prefix. NativeDef reuses Signature. The verifier derives the canonical layout from the last Function default's prefix and checks all other default entries for consistency. Read-only prefixes can use Value or Cell and must agree across entries. Parameters outside every default prefix remain Value. VerifiedProgram stores a compact read-only layout with the shared signature, charging construction and checks to work and retained capacity to the program ledger. Calls read the verified layout without rescanning defaults. Native default entries still have no script lexical captures and receive earlier shared parameters through the internal prefix path.

Natives use the same ordered preparation. The VM exposes a native Entry only after all defaults and type checks succeed. The shared Cell environment and host argument array are separate. The ticket shows bound author values and keeps Cell handles internal. If stages such as CallScript change relevant Cells, the VM projects a fresh contiguous argument view before publishing a resumed ticket. The original native entry runs once. Natives without defaults keep the Value fast path, with no extra Cells or environment window.

Parameter preparation has explicit stages for Cell creation, type checking, prefix passing, writing the default result, and entering the body. It publishes target roots before clearing source roots, preserving identity through budget suspension and GC. A preparation failure propagates from the original call site, before the body's handler is entered. Each stage uses work and allocation allowances.

Const stores full int64 and float64 bit encodings, UTF-8, Bytes, and specified immutable structures. The disk format uses little-endian integers and u32 indices. An editable compiler instruction occupies 16 bytes, with a u16 opcode, zero flags, and three u32 operands. Editable PCs are instruction ordinals. Verification maps those ordinals to u32 execution-word offsets. The encoded package stores a shared compressed word stream with packed opcodes and operands, as defined in the [bytecode format](../crates/aside-vm/src/bytecode/FORMAT.md#instructions). Complex operations reference typed descriptor tables. Constants, symbols, functions, modules, registers, and PCs all have distinct index types. The encoder writes field by field. A package contains no runtime Value, HeapId, root token, or Rust memory layout.

The executor accepts only a VerifiedProgram with private fields. Decoding and verification check lengths and total limits before allocation, then check indices, windows, jumps, captures, signatures, default entries, exception and cleanup regions, control flow, native versions, and capabilities. Unknown opcodes and missing capabilities report their location. Dynamic types, initialization, read-only writes, and effects remain runtime checks. Loading and immutable code have a separate capacity ledger.

One instruction specification defines operands, register reads and writes, branches, throws, suspensions, and descriptor tables for the encoder, decoder, verifier, disassembler, and dispatcher. Instruction families cover values and bindings, cells and globals, numerics and strict bool control flow, closures and calls and returns, collections and classes and members, patterns and iteration, exceptions and finally, and yield, await, and tasks. Children and property references lower to common operations and descriptors under their established semantics. Compiler and executor share these definitions, including opcode numbering and operand meaning.

**Contiguous frames and scannable root ranges**

Hot registers use VM-owned contiguous FrameSlots windows addressed by base+Reg. One window stores the registers without per-register objects, RootTokens, or BTreeMap entries. Frames reuse bounded windows. A separate bitmap tracks uninitialized states, and null remains an ordinary value.

Every script or native push and every saved finally exception checks a contiguous free span for the operation's full set of windows. When the shared pool needs compaction or growth, budget preflight for the original call includes growing root descriptors and indices, window maps and free tables, initializing buffers, moving root values, and allocating all new buffers. Insufficient budget preserves the original call site and retries admission against the pool after yielding. Admission succeeds before argument borrowing and window registration, and publication stays in the original call transaction. Defaults, class initialization, sort comparators, and native callbacks use the same admission. Overlapping buffers count against the heap byte limit. Host capacity and per-window limits also apply. Root tokens, GC scan identities, and snapshot layout stay stable, and cancellation releases the task's registered windows.

For each fixed-length range, the Heap registers a RootRangeToken with HeapId, SessionEpoch, and a generational RangeKey. It stores only owner, kind, length, and cursor. Each GC step temporarily borrows the VM's RootRanges to find the slice. Heap stores neither addresses nor long borrows. Registers, arguments, native temporaries, exceptions, and delivered results all have ranges. A persistent host reference can still use a single-value root.

A root range starts with valid null slots. Registration and provider mapping publish together before GC can see it. The insertion barrier then publishes each real value. Removal unregisters before freeing a window. Overwriting, moving, argument copying, and delivery apply the barrier before the write and publish the target root before clearing the source. Root scans advance by descriptor slot, generation, and element offset, charging holes, descriptors, and individual values separately. Reusing a slot resets the previous cursor. Physical movement updates the map only at safe points and retains logical identity, length, and order. A short borrow must end before movement or reentry.

A live root range with a missing provider or wrong length is a runtime invariant error. An ordinary `gc_step` call with external ranges must use the same provider or reject the missing provider explicitly. The common weak-reference cutoff follows completion of single-value roots, all ranges, and gray work. Total bytes include window capacity, bitmaps, frames and continuations, descriptors, reserved buffers, retired slots, and overlap during movement. Accounting releases only freed capacity. Internal VM interfaces prevent direct slot writes from bypassing the barrier.

**Restoration, calls, and results**

A session's Vm shares one Heap, FrameSlots, and module instance set across a bounded collection of tasks. Each Task keeps its own execution stack, unwinding, waits, delivery, cancellation, and sliced operations. The scheduler selects a Task within the Vm for each slice. While one task waits externally, others can access the same globals, objects, and closure cells. Host tickets, waits, and deliveries include TaskId. Completing or revoking a task releases its own state. Independent sessions use independent Vms, and all task metadata uses its session's budget.

A function's Context declares its restrictions. The effective context accumulates NoWait, Init, and Derived over the call chain and narrows effects. Every restriction stays in force through a call and the caller's context resumes on return. Host tickets carry all effective restrictions. CallScript and ordinary calls use the same rules.

ScriptFrame stores FrameId, fixed CodeRef and ModuleInstanceId, PC, window, closure and receiver, argument binding phase, return target, effects, owner and region, exception unwinding, and the current operation phase. NativeFrame stores a versioned continuation and strong reference slots. Source error nodes and unresolved diagnostics are excluded from executable lowering.

Function declaration restrictions and effective call-chain restrictions are separate. Current public analysis entries can represent declarations with Ordinary, NoWait, Init, and Derived. The VM retains a simultaneous Init and Derived restriction in its accumulated flags. If future analysis produces legal combinations of declarations, the shared format and all consumers must support them before the entry is exposed.

AnalyzedModule retains the analysis entry context, each function's kind and declared effects, and stable symbol and module identity. Lowering uses these facts to generate FunctionDef Context and signature. Runtime accumulates effective call-chain restrictions. Import and namespace member resolution retain the declaration module and export identity, and re-exports additionally retain their resolved origin. Trusted native registrations supply stable symbols and versions, ABI, capabilities, effects, and default implementations. Analysis retains the reference identity. Package construction verifies it against the linkage input and emits NativeDef. Missing or conflicting linkage produces a source diagnostic.

`run_slice` takes instruction, internal work, allocation, and clock allowances and returns Returned, BudgetYield, HostCall, Waiting, Fault, or ResourceBlocked. ResourceBlocked means hard capacity for a complete fault record is unavailable. Section 23 defines retention, restoration, and cancellation. Long comparisons, spreads, and matches charge work in explicit phases. Ordinary functions use common call binding.

Trusted hosts can register a pure native as a read-only leaf computation. It borrows the current Heap and bound arguments and returns a scalar without allocation, external state, callbacks, or waiting. The VM charges declared work to the current SliceBudget and enters existing Commit and Release after successful preparation. If the computation rejects the input, the normal native entry produces the original error. With fixed binding, builtin type checks, and at most two arguments including the receiver, a full allowance preflight can use the caller's arguments and write back directly without a NativeFrame. An insufficient allowance yields within ordinary binding preparation. If the read-only attempt declines, it preserves the normal call path and that path's allowance. The pure computation may be repeated to produce the original error. Success checks the deadline again. A host registration supplies the function pointer and reconnects it on restoration. ASB and snapshot versions stay the same.

A host registration can set `standard_derived_commit` to let the VM synchronously commit an existing standard derivation. The atomic host operation charges one work unit for entry and one for commit. Dependency changes and allocation follow hard heap allowances, and the charge is independent of dependency edge count. The VM reserves allowance before the operation, retains Commit or fault state and checks the deadline afterward, then uses normal return checks and release. Without registration, it retains the CallbackReturned ticket and opportunity for host reentry. Restoration reconnects the registration using the current ASB and snapshot versions.

HostCall registers state and argument roots before exposing the response ticket. A ticket includes call sequence, native symbol and signature version, task and owner, and source position. It accepts one response. Arguments are available through short borrows only. Returned and Fault data remain in VM delivery roots or owned host roots until transferred to another registered root or owned handle, or explicitly discarded. Taking a bare Value leaves the original delivery root in place.

Ready publishes the result before committing the return slot and advancing. Pending saves the wait descriptor and successor phase. CallScript retains NativeFrame and then pushes a callback in the same task. Continue saves the algorithm phase for the next slice. Error unwinds from the original call site. Dispatch, waiting, commit, and completion are distinct resumable phases. Restoration never repeats a native entry that already took effect. Snapshots use logical IDs and code versions and allocate new objects and root ranges on restore. Runtime tokens stay out of the snapshot.

Captured cells use the existing Cell object kind. It stores initialization state, fixed mutability, and a contract versioned with code and module. CellNew(binding) creates an uninitialized object from the binding descriptor and stores the handle in the specified register. BindInit initializes once after the type check and barrier. CellRead and BindRead check initialization. CellWrite and BindWrite check initialization, mutability, and type. Ordinary field writes use the same contract. Capturing a handle in Cell mode retains shared state, and reading happens when the function executes. Forward read-only captures can use Cell. A provably initialized read-only capture can be stored by value. Null is a valid initialized value. GC, closures, and snapshots retain state and contract.

Module root declarations and lexical locals in the initializer have distinct binding identities. Only a true module-context root declaration belongs to the global table. Block, conditional, loop, and catch locals belong to the initializer regardless of whether owner is empty. A static BindingId identifies the binding site. Each entry into the scope replaces that site's Cell handle with CellNew. Closures from the same entry share it, and earlier closures retain their earlier Cell. All entry CellNew and Clear operations precede construction of named closures. A `continue` back edge to the `while` condition passes through the corresponding entry. Only the dedicated catch entry initializes its binding once. A default entry captures the definition environment without recreating that environment's local Cells.

An enclosing external lexical binding retains its original identity and nested capture relationships. It is distinct from a local declaration of the entry or an ordinary host symbol. If compilation lacks an actual external Value or Cell link, lowering reports MissingLink at the source location. Trusted direct native links follow their own contract.

A binding descriptor stores type, mutability, and initialization requirements, which also govern shared cell writes. Match initializes outputs only on success. MemberGet binds a receiver for a class method and leaves an ordinary table closure as a plain function.

An argument spread container is private to the current call. A sliced shallow capture of an array checks the complete content version from beginning to end, including overwrites, insertion, removal, and reordering. On change it reports ConcurrentModification without calling the target. The outer tuple is immutable. After capture, source changes leave the captured outer sequence valid. Inner object changes are visible through shared references. Cursors, version, partial capture, and storage awaiting release count toward capacity and roots. Failure uses existing exception cleanup. BudgetYield retains intermediate state and stays separate from external waiting.

Collection spread uses the same sliced shallow capture. `[...source]` accepts arrays and tuples, `{...source}` accepts tables, and null or other types raise Type at the spread position. Each spread finishes capture at its source position before later expressions run. Explicit table keys and values still all evaluate before the table is built and its keys checked in written order. An invalid spread source fails when encountered. Later overwrites preserve the first position of a key. The result is published after the entire expression, and exceptions or cancellation release unfinished containers. Bytecode uses ArrayPush, ArraySpread, and ordered TableSources descriptors. TableSpread copies verified own slots. An empty destination uses a linear copy. Merging into a populated destination compares only existing destination entries and does not scan source entries just appended. Work and allocations follow the existing allowances without a separate collection-length limit.

Assignment locations and arguments follow source evaluation order. Signature binding begins only after all actual arguments have evaluated. Ordered argument storage retains duplicate names until the final binding phase reports conflicts. Ordinary calls without spreads use a contiguous argument window. A spread captures its elements at the source position, so later argument side effects cannot change that captured sequence. Mutable captures use shared cells. Loop iterations bind independently, and upvalues do not store movable window addresses.

**Exception regions and cleanup**

The verifier checks ordinary control flow for protected regions, catch, and finally. It rejects Jump, Branch, or fallthrough into a handler. Normal exits from protected regions and catch use Leave. Return and throw use common unwind cleanup. A throw in catch goes to the outer handler. A new exception in finally continues outward. Each EndFinally matches the active unwind record. Ordinary cleanup calls inherit NoWait.

## 23. Complete fault records and lifetimes

This section defines complete fault records, propagation, and restoration.

### Author-visible behavior

`catch` binds the original thrown value. Strings, integers, null, and objects retain usual value semantics, including original object identity. `throw;` rethrows the same fault from the lexically innermost active catch of the current function, retaining identity, code, original location, and original stack. `throw value;` creates a new fault with a new location and stack even if the value is the one previously thrown.

`std::core::error_info()` returns a read-only view of the nearest active catch in the current call chain, or null. Ordinary helpers and native callbacks on the same task share the call chain. Each task queries its own context. A catch is active from handler entry through exit from its scope and is already exited on entry into finally. See [source documentation](../crates/aside-std/src/core.rs) for view fields, stack records, and cause iteration.

FaultInfo is a traced, read-only view in the same heap. Retaining it keeps the complete fault, and ordinary reachability controls collection after variables release it. The view exposes value, code, origin, stack, and typed causes. The author object referenced by value keeps its original mutability. The query depends on execution context and declares a diagnostic-read effect, so a pure derivation reports an effect diagnostic. Runtime language errors use a core.Error value with a fixed code, message, and read-only details. Authors can throw any value. The envelope's stable code comes from a versioned registry. A same-name field in an author table stays ordinary data.

A host reports specific reasons for native API errors through `Vm::respond_language_error(ticket, kind, details)`. The original frame roots details, and ordinary FaultBuild includes them in CoreError through the same budget, cancellation, and snapshot paths. Pass null when there are no details. String interpolation on CoreError uses string details if present, otherwise the fixed message for its code. It does not traverse arbitrary objects or call script conversions.

A new fault normally links to the nearest active catch's complete fault in the same call chain. An explicit native cause takes precedence over that implicit catch link. A relationship created when finally replaces an exit remains separate. Cross-task causes link through explicit task and wait propagation records.

### Fault graphs in the shared heap

ErrorEnvelope, chunked stack records, and cause nodes use private object kinds in the existing Heap. FaultId wraps a full HeapHandle. General field writes and object construction preserve this encapsulation. Copying an ID follows ordinary handle rooting rules. Access checks heap, epoch, generation, and kind. One registered fault root retains the original value, stack, causes, and referenced code versions.

After construction, fault identity, original value, code, origin, and original stack are fixed. The VM appends cause relations while existing nodes retain their contents. FaultInfo exposes those relations by kind.

- CaughtFault links the active catch at creation of a new fault.
- ExplicitCause links an original fault provided by native code or explicit wrapping.
- AwaitedFault links the full producer fault and the stable wait activation for this await.
- ReplacedExit records an exit that finally actually replaces, with the replacement site and Throw(FaultId), Return(Value), or Leave(CodeRef, target). Hard owner or region revocation follows task termination.

A fault can retain both a catch cause and a replaced Return. Existing causes stay attached. Each unwind event has a stable identity and is appended once, including after yield. Rethrow and explicit forwarding can create shared references or back edges. The diagnostic cursor records visited identities and prints references. GC, snapshots, and diagnostics traverse with explicit cursors. The original stack is captured once. A failed await creates a separate envelope for each actual waiter. The producer fault supplies value and code. The consumer's await position and call chain supply origin and stack. AwaitedFault links to the full producer fault. The producer record stays intact and each waiter retains its own propagation chain. The snapshot includes stable wait activation, delivery and FaultBuild phases, and the identity of any wrapper already created. The producer stays rooted until the full wrapper root is published. Yield or restoration does not build a second wrapper. A later await uses a new activation. An active catch at await also contributes its ordinary cause. Wrapping follows the same FaultBuild and capacity rules.

Exception routing uses the current throw, rethrow, or call PC and any consumed regions. Diagnostics use the original fault location. When an inner catch handles an error inside finally, the outer pending exit stays active. When an error escapes finally, the VM publishes the complete old exit in the cause graph before clearing its unwind root.

### Native frames, delivery, and catch roots

A host response uses `Error(NewFault { value, code, cause })` to create a new fault or `ForwardFault(FaultId)` to propagate the complete fault retained by the current native. Forwarding unwinds from the original call location. Comparing original value bits serves only value semantics. Explicit identity determines fault forwarding.

NativeFrame retains bounded fault slots alongside continuation values for accounting, scanning, and snapshots. CallbackFault enters a slot before the callback frame is released. Continue and Pending retain these slots by default, and later phases can read them. Before another CallScript, move faults still needed into explicit continuation slots or mark them handled. Retention policy uses Preserve or Replace(ids), with an empty set meaning handled. Ready publishes its result before releasing remaining faults. Error and ForwardFault publish target fault roots before clearing sources. Cancellation releases all slots through the same sliced cleanup.

`delivery_value` reads the original value without consuming delivery. `delivery_fault` returns the complete view. `take_fault_delivery` transfers the entire envelope to a host root with a lifetime independent of the Task, then releases the delivery and task slot only on success. The returned FaultRoot owns its root and must be released explicitly. To copy only the original value, use `copy_delivery_value_to_root`. The original fault delivery remains until explicit discard. A unified take interface can also return an owned result tagged Returned or Fault.

Each retained catch record includes FrameId, RegionId, and its activation. On control transfer, the VM first publishes target roots for rethrow, cause, and pending exit. It then removes catch records for scopes actually exited and commits the PC update or frame release. Outer catches enclosing the target remain active. Ordinary helpers preserve active catches in parent frames. Normal reachability retains original values copied to author variables or closures. Capacity counts concurrently active catch and unwind records, so sequential independent catches reuse space.

### Stack capture, budgets, and hard capacity

FaultBuild is an explicit resumable Task stage. It first retains the original value, original fault, and pending exit, then captures the versioned stack in chunks. Relevant frames remain until the record is complete. Other tasks can run. Only a complete fault reaches catch, native code, or delivery. Each stack record contains fixed code, module, and source-map versions, function, PC, and frame kind. It retains the actual code version. Original execution state still roots local variables.

Stack chunks, cause nodes, cursors, code versions, native slots, retired space, and release queues use their respective capacity ledgers. Barriers run before publishing roots and edges, then sources clear. Stack capture, cause insertion, scanning, and release are sliced by work allowance. Insufficient budget returns BudgetYield with the work required. Resumption stays at the same phase and does not replay the throw or native action.

An ordinary resource error can become a catchable core.Error when the complete record fits. If fault construction itself hits hard capacity, it returns `ResourceBlocked { task, resource, current, required }` to the host using reserved task control state. Roots, frames, and the build cursor remain intact. The host can collect or release resources, raise an allowance within permitted bounds and resume the same phase, or cancel the task. `required` is the known minimum for the next step. The task remains blocked until the fault is complete and retains all past side effects. Actual process allocation failure follows platform policy.

`invoke_sync` retains its cumulative hard budget. A ResourceBlocked in that path ends synchronous reentry and reports a resource failure to the host, with bounded cleanup. It returns owned success or fault, or an explicit control failure, and retains prior side effects. Ordinary resumable tasks use `run_slice`.

### Fault snapshots

A snapshot retains the complete fault graph with sharing and back edges, code registry version, fixed code, source map and native versions, active catches, pending exits with routing PC, consumed regions and finally phase, FaultBuild cursors, native fault slots, and unclaimed deliveries. It saves the identity of each relation insertion. Restore creates new object identities and then connects the graph. Old HeapId, FaultId, and root tokens remain invalid. Missing version errors identify the exact affected location.

The executor and compiler share a bytecode model supporting ordinary calls, classes and inheritance, script modules, collections, indexing and members, call spreads, and rest. Named table spread lowers to ArgsSpread. The host coordinates complete owner revocation. `Vm::cancel(owner)` only cancels tasks, while independent host roots confirm release through their retirement records. Retirement requires bounded cleanup of single roots, non-task RootRanges, task state, and external resources. See [the engine's owner revocation contract](engine-architecture.md).

### Synchronous validation of host properties

A host object can retain a static HostPropertyValidator with a stable name, version, and pure callback. The callback receives a read-only PropertyRead of the proposed graph, receiver Value, resolved fixed property index, and new Value. It returns before normal assignment commits. Validation runs without calling script, waiting, or modifying the heap. Failure becomes a catchable language error at the assignment and preserves the old value. `alloc_host` and `alloc_composable_host` explicitly take an optional validator. The object owns the metadata and no extra capability registration is needed. Private field updates use `set_host_payload` and the common GC barrier. Retirement clears the property table and private strong edges, disconnects dependent derivation, freezes its last valid value, and removes queued recomputation. A direct access to a retired host returns RetiredHost, which becomes catchable InvalidState at the access or host call site. Damaged and cross-heap handles remain distinct errors.

Source spans use the first and last meaningful syntax tokens, excluding leading whitespace and comments. The source file path and logical module identity are stored separately. The window displays the path, line and column, and any string or scalar a script threw.
