# 视觉资源自动准备提案

目标是让作者只描述最终要显示的画面。控件的候选图片来自 `image_skin`。构建器在 ASB 内保存可静态确定的剧情图片计划，播放器在对白揭示或推进处用当前调用位置查询下一次 `image` 或 `layered_image`。分析能越过含翻译的对白、进入捕获已知值的 `stage.transition` 回调、解析局部表字面量和普通函数转发。对大型图层目录和未挂载页面的分析仍需扩展。现行合同见[引擎架构](engine-architecture.md)。

Shin 的执行链说明了两个不同的时机。执行 `LAYERLOAD` 后开始加载，准备好才替换图层。立绘另按表情选块，多套表情可以共享身体。Reel 可直接从皮肤取得有限的未来状态，而剧情要提前到上一句准备，仍需要下面的控制流信息。[Shin 图层加载](https://github.com/DCNick3/shin/blob/2405086f8a1d319c9df3605df38a4f0a6379a42d/shin/src/adv/command/layerload.rs#L135-L228) · [Shin 立绘](https://github.com/DCNick3/shin/blob/2405086f8a1d319c9df3605df38a4f0a6379a42d/shin/src/asset/bustup.rs#L87-L110)

## 从哪里知道下一幅画面

构建游戏时，由 Reel 从已解析的调用和控制流提取接下来会使用的逻辑资源。Aside 只提供通用的函数、基本块、常量和调用信息。图片路径、图层描述和控件状态由 Reel 理解。预测结果随对应代码产物生成，开发运行和发行包共用分析；作者只维护绘制所用的素材。

优先支持传给图片构造器的常量路径、可静态解析的函数转发，以及由常量键选取的只读图层组合。相同组合共享资源表，每个调用位置只引用组合编号。把查询与渲染接在同一个组件上尤其重要。例如 DDLC 的 `show("sayori", "4p")` 最终通过角色对象写入表情，再由 `layered_image` 从目录取三个图层。普通方法名和两个字符串本身无法证明这个关系。若现有包装跨越了可分析的动态调用，把组件调整为接收**绘制实际使用的表情值**，允许剧情直接传这一个值。组件继续决定位置、移动和叠放。这样既能在调用处识别素材，也能画出同一套图层。首版只处理能说明来源的表达式；分析遇到可变表、未知调用或复杂循环时，在限定工作量内结束。

构建产物按函数和调用位置索引资源组合，计划上限为 1 MiB。遇到普通返回时，播放器继续查外层调用位置。只选已知路径上最近的一组画面，连续台词指向同一组时沿用在途工作。分支指向同一张图时可以预取，其他分支等路线选定再准备。计划引用程序内的字符串常量。台词、随机数、存档、声音和页面构造仍在实际调用处执行。没有候选的图片按实际显示需求加载。

Ren’Py 也从当前剧情位置沿控制流寻找图片。Reel 的调用可以包含任意 Aside 代码，把可提取的资源引用留在构建阶段，有助于限制玩家端每次推进的工作量。[Ren’Py 图片预测](https://www.renpy.org/doc/html/config.html#var-config.predict_statements)

## 菜单、内存和快进

控件已经知道自身的候选内容。按钮可从现有皮肤取得焦点和按下状态用图；导航项获得焦点或指向时，可取其目标页面构造函数里能确定的首屏素材。列表沿用视口和滚动方向，准备即将进入的行。任意隐藏节点可能是未解锁的图库或长期停用的页面，单凭隐藏状态无法判断打开时机。

播放器把候选直接送入现有资源队列，复用当前平台、语言和资源版本下的在途请求与已驻留图层。预测按低优先级使用既有预取份额，前台读图和媒体优先。连续快进时以最新位置替换尚未开始的工作；选择改道、关闭页面或读档时撤回失效请求，读档从恢复的位置重新计算。命中时由可见请求接管；错过时沿用正常加载和呈现流程。首版负责读取和解码，GPU 上传单独计时。

## 迁移和验收

已挂载的隐藏模态界面由播放器根据可见性准备打开时会显示的素材。剧情调用按真实图层描述选择自动预读，运行时才能确定的表情由可见需求直接加载。用 DDLC 的背景、首次立绘和换表情对照这两条路径，用 Euphoria 设置和海猫历史检查首次打开、重开和滚动。

在同一发行播放器中交替开启和关闭内部预测，保持相同输入和演出时长。比较首次换图、热缓存重放、连续快进和选项改道。冷读波动另用受控读取延迟复现，和实际磁盘结果分别记录。记录换图指令到首次提交、当前对白或动画的帧间隔、实际读取与解码、丢弃字节、内存峰值，以及构建时间和包体增量。检查自动预测能否达到手写对照的换图时零读取、零解码，同时避免上一句出现新尖峰。错误预测、资源缺失和读档恢复都应沿用实际游戏的状态、呈现和源码诊断。
