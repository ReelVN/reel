# Reel engine architecture

[简体中文](engine-architecture.zh.md) · [Engine documentation](README.md) · [Aside language specification](aside-language.md) · [Creator guide](https://reelvn.com/en/docs/quickstart)

This document defines module responsibilities and behavior across modules. Interface parameters and defaults are documented in English beside their declarations.

## Creator model

Reel lets creators write visuals, dialogue, UI, stage direction, and embedded 2D games in code. Functions organize flow, nodes compose the scene, and activities express changes over time. Pages, story, and gameplay share the same state, input, and lifetime model.

The project entry point is the `main` function in `src/main.aside`. It configures the project, establishes shared state, and starts the flow. Modules can group chapters, menus, character scenes, or minigames. A simple view returns nodes, a function that waits for interaction returns a result, and a component that needs ongoing control returns an object with explicit methods. Callers pass in shared state. Components own their local state.

A view declares the named nodes it exposes to callers through a structural type. A menu declares its possible results through a union of string literals. The Aside compiler and editor share declarations, and the VM checks dynamic values at ordinary function and binding boundaries.

Ordinary functions can wait for dialogue, activities, and interaction results. `spawn` creates a concurrent task. `sequence(...)` combines actions in argument order, `parallel(...)` runs several actions concurrently, and `repeat(...)` repeats an action. Compositions can nest. Start an action with `action.run()` and use its activity handle for pause, resume, stop, and completion. A `scope` owns temporary nodes and work. A `reading` block groups dialogue, choices, history, and reading state for a portion of the story.

Creator-facing interfaces use one stage model for position, layout, images, text, styling, input, and effects. The player's stage background is black and remains visible wherever nodes leave it uncovered. The engine reuses prepared data and resources, and skips repeated work on stable scenes using invalidation information.

Aside depends on language and foundational Rust libraries. Window and GPU types stay in platform adapters. The UI supplies portable frames with owned data and resource leases to backends. `reel-engine` currently depends directly on `aside-compiler`. Source and ASB use the same host registration and execution admission checks.

The host UI thread owns the widget tree. Its pinned version of `tree_arena` provides flat node storage and an API that borrows parents and children separately. Frames and presented geometry own the data they carry across threads. The tree stays on its own thread. Input path capacity accounts only for the event routing array.

The shared player talks to the host, rendering, media, storage, and input through HAL contracts. `reel-player::hal` defines host lifecycle and display control. The respective crates maintain the rendering, decoding, and storage contracts. The player advances sessions, handles resource readiness, accepts presentations, dispatches input, and handles suspension. Platform assembly creates the device and event loop.

`reel-player::distribution` opens the ASB, text pool, language index, and resource root in a distribution, then passes them to the shared session for execution. The CLI locates creator projects and handles compilation and export. Platform entry points open distributions directly.

`reel-web` provides the browser entry point for website code previews. The editor submits a complete `src/main.aside` to the same Aside compiler using the `web` build target. Diagnostics report zero-based lines, UTF-16 columns, and UTF-8 byte offsets. Each successful run creates a new session. The page supplies the canvas, input events, and binary assets keyed by their logical paths. The browser and distribution tooling share effect shader preparation. Generated WGSL effects mount in the session alongside assets supplied by the page. Previews reuse the engine's stage and the player's rendering path, and release the session on close. This entry point runs and demonstrates example source.

The browser editor uses a Web Worker to query `aside-lsp` for completion, hover, and diagnostics on the current `src/main.aside` buffer. Its queries use the same Reel interface declarations and UTF-16 LSP positions as the desktop language service. The language service runs independently of WebGPU and stage sessions.

Creators build the distribution player with Cargo from the Reel source tree. Build `reel-game` for desktop and use `cargo vita build eboot` to build `reel-vita` for Vita. Outputs follow Cargo's target directory configuration. Then use `reel export --release --runtime <player-path>` to package the player with the project. Default startup assets are in `crates/reel-player/runtime/vita/sce_sys/` and can accompany the Vita runtime.

Release exports for the native desktop target, `desktop`, and custom resource variants include the tool bundle's host player by default. Specify `--runtime` or `--data-only` when shipping to another desktop system. Desktop export preserves the runtime files' relative paths and writes the project package to the export root. A runtime file that conflicts with a package name raises an error.

A project can set its release title, reverse-domain `id`, and optional square PNG icon under `[desktop]` in `distribution.toml`. Windows writes the application icon into the staged EXE. Linux provides a script that registers the app in the current user's application menu. macOS puts the runtime in `.app/Contents/MacOS` and the project package in `.app/Contents/Resources`. The standalone player reads the release identity beside the game package, sets the initial window title, and uses `id` to locate the system's per-user save directory. Export prepares the platform shell and preserves the common ASB and resource formats.

The read-only `target` string in `reel::build` records the build target. `--resource-target` selects both the source constant and the resource overlay directory. It defaults to the host system name and is included in the compilation cache key. Use an ordinary branch such as `if build.target == "vita"` to select effect settings. The compiler removes execution code for the unselected branch. `window.info().platform` reports the current player's platform. Resource collection follows the directory overlay and packaging rules.

`reel export --release --resource-target vita --runtime <player-path>` exports a VPK and a game data directory for the current game. The default destination is `dist/vita/<TITLE_ID>/`. Use `--output` to set a different directory. In the project's `distribution.toml`, the `[vita]` keys `title_id`, `title`, and `version` identify the installed app, its LiveArea title, and the distribution version. `--runtime` accepts a Cargo-generated SELF or a runtime directory with `eboot.bin` at its root. The directory can contain default `sce_sys/` startup assets. `[vita].assets` can point to a project startup asset directory and its `sce_sys/` files override corresponding defaults. The CLI uses VitaSDK to produce `<TITLE_ID>.vpk`. The neighboring `data/<TITLE_ID>/` contains the ASB, text package, and resource volumes. Distribute both together. `--data-only` explicitly exports code, text, and resources for development and performance tooling.

The player installs the VPK and copies `data/<TITLE_ID>/` under `ux0:/data/reel/games/`. At LiveArea startup the runtime uses the current app's Title ID to open `ux0:/data/reel/games/<TITLE_ID>/game.asb`. The neighboring `saves/` contains progress and project settings. When publishing an update under the same Title ID, replace the distribution files and keep `saves/`. Exiting the game closes the player, media, and rendering device. Performance builds can launch a given package through an explicit request.

Platform implementations live in modules of the existing crates according to their rendering, media, and host roles. `cfg` selects implementations at module entry points and in target dependencies. Shared interfaces pass capabilities, resource descriptions, and owned data. Native handles stay in adapters. Backends share resource formats, and production implementation retains `forbid(unsafe_code)`.

The Vita host loads the distribution directly, maps the authored canvas onto the fixed physical display, and passes controller, touch, and suspension events to the shared player. A pinned Git commit of `vita-native` provides native calls and encapsulates SDK handles and native completion reclamation. Reel's adapter provides shader interfaces and vertex layouts. WGPU and GXM share draw planning, resource requests, and cache policy. The device adapter manages programs, texture storage, coordinate conventions, submission, and completion reclamation. Texture preparation uploads blocks in the order specified by the container. Audio goes through shared Opus decoding and mixing into AudioOut. The AvPlayer factory provides owned video frames and PCM. Platform assembly sets device memory limits and accounts for buffers, queues, and GPU residency separately.

GXM puts uploaded source images and software video planes in CPU-uncached MAIN memory, and puts glyph atlases, render targets, and scanout buffers in CDRAM. A source image keeps one physical allocation. Offscreen effects continue to sample intermediate CDRAM results. Offscreen targets use linear storage by default. With `gxm-tiled-targets` enabled, an RGBA8 target with both axes at least 32 pixels uses 32×32 tiled storage in frames that need no background snapshot copy. Tile planning accounts for full tile padding. Frames with background snapshots retain the linear PTLA path. Allocation and caching record actual layouts and bytes. Smaller targets, Coverage8, and scanout stay linear. Native admission tracks actual kernel blocks. CPU arenas and graphics MAIN blocks share the process ledger. Scanout and pixel blocks share the CDRAM ledger. Physically contiguous video memory has separate admission. Initialization obtains capacity from kernel free space, after parameter buffer creation for CDRAM. Each block includes page-aligned capacity. The ledger releases a charge after the last user completes and physical release succeeds. Pools suballocate by lifetime and size, with a reclaimable free-space cache target.

The renderer plans frames against physical domain capacities and accounts separately for resource payloads, offscreen targets, and staging data. Payload statistics guide working-set planning. Physical page accounting governs allocation admission. The current frame, preserved transitions, and in-flight readers hold required storage. Rebuildable caches use remaining capacity. Under allocation pressure, the renderer reclaims idle blocks and render caches in the relevant domain, then retries once physical release succeeds. Existing submissions hold resources until completion. Upload queues and in-flight frame limits cap concurrency and transient peaks. Exhausted kernel page allocations enter the same reclaim path. Errors preserve requested size, occupied capacity, available kernel free space, and the original return code. After reclamation, the renderer waits only when an existing submission can release storage. It rejects the current frame if its working set still cannot fit.

Shaders compile to backend-specific programs. Desktop WGPU uses WGSL, and GXM uses the SDK's offline `psp2cgc` to generate GXP. Built-in programs ship in the player. Creator effects use the same typed expressions to generate target programs and parameter bindings. Devices reuse created programs and blend configurations. Offscreen targets allocate to actual coverage.

A node's `effect_resolution_scale` sets the raster resolution at which its `effect` computes output. The default is `1.0` and the range is `(0, 1]`. The effect computes at the reduced raster size and scales linearly back to the original output region. `Fragment` retains its logical position, dimensions, and sampling coordinates. Subtrees and independent masks use their own resolutions. A game can choose a scale for a specific platform with `build.target`. The renderer plans intermediate targets, budgets, and caches using the explicit scale. The `reel::effect` host interface and shader uniform ABI retain version 1.

When compilation proves that one coordinate axis of a sampling reduction is constant, it can include a single-axis GXP variant for ordinary color output that moves mapping and bounds clipping on that axis outside the loop. The runtime selects it for an actual source mapping with a finite diagonal matrix. The variant preserves sample count, coordinate expressions, accumulation order, and quantization boundaries. Outputs use the `REELSHD2` container with independent code section boundaries and uniform ABI version 1. All code segments and runtime programs share the existing shader-size and resource budgets.

Independent color effects reuse results based on their source commands, parameters, textures, and actual raster size. When the command range for a transition's replacement or inserted pixels intersects the effect source, the renderer recomputes from the current draw. Source masks and blending take part in admission. Other subtree masks and transitions can update independently.

Sony compilation uses precise math and integer semantics, with `-O3` by default. On SDK error `D7203` for fragment register capacity, compilation retries once with `-O2` using the same input and precision settings. If the retry also exceeds capacity, diagnostics from both attempts are kept. Register spills remain errors, and the cache identity includes both optimization levels and the retry rule.

When compositing requires a background snapshot, shared planning determines copy bounds on the same integer pixel grid. A first-use, single-sampled target with matching format and full physical coverage uses a texture copy. A partial first write combines the clear and copy draw in one pass to avoid clearing and then rewriting the same pixels. Existing target content, multisampling, and surfaces that need coordinate resampling use draws as well. Both backends save the background and sample snapshots in the original composition order. GXM uses fragment and transfer dependencies, and WGPU uses ordered encoding. Both retain resources through the copy and subsequent reads.

With `gxm-tile-destination` enabled, GXM directly reads the current pixel output register as the blend background on eligible single-sampled RGBA8 surfaces and can omit the background texture copy. Shared planning and execution use the same eligibility rules. Source subtrees composite independently, preserving quantization boundaries and draw order. Additional masks, transition inputs, and other surfaces continue to sample snapshots.

GXM scene submission, fragment completion notifications, and the display queue manage drawing, resource retirement, and scanout separately. Submission retains referenced buffers, textures, and targets. Host polling checks scene and transfer notifications individually and reclaims completed leases. Each of the three scanout buffers owns a display sync object and is reused after release from the display queue. Offscreen surfaces keep their own pixel storage and establish dependencies through scene order and fragment or transfer flags. Compatible surfaces share scheduling targets, and scene valid regions limit the area drawn. The display callback wakes the host after screen submission and scanout synchronization. It publishes completion before waking. The host thread advances scripts, UI, and resource management. The device owns the wake object until the display queue drains. Kernel blocks, GPU mappings, context ring buffers, and scheduling storage for render targets are each accounted for by actual capacity.

A consecutive offscreen RGBA8 effect chain with the same raster and a single consumer can combine into one GXM scene under Sony's macrotile synchronization rules while preserving sampling, quantization, and logical sizes at each stage. Shared offscreen planning first produces independent subtrees, then executes composition and terminal effects on the parent target in original draw order with their shaders, transforms, clipping, and opacity. A source target consumed later is charged for its full lifetime. The budget determines the size of the production window. Chains with the same layout in that window can occupy contiguous cells of one macro target, with at most 16 cells per allocation. The renderer admits the full linear atlas and scheduling storage configured for macrotiles. The native layer lays out cell targets by column and gives each an independent CLAMP texture alias. It translates viewport and clip and checks for monotonic drawing and read-only access to preceding cells. Aliases share the pixel owner, and caches and in-flight readers retain the actual allocation. Subsequent frames on the same queue and same-frame chain segments after the last parent read can reuse an entire atlas with identical layout and cell dimensions. Overlapping lifetimes and atlases holding effect cache entries stay exclusive. Every use reinitializes its cells and only the last use of the atlas in that frame can publish new effect cache entries. Admission accounts for the peak of whole atlases alive at once. Masks, background reads, branches, and capture boundaries continue to use independent targets.

The Vita distribution entry point requests Sony power configuration Mode C and 444 MHz for the ARM CPU at startup. Mode C keeps WLAN enabled, raises GPU performance, limits display brightness, and disables the camera. Actual clock rates depend on system and device plugin settings. Performance records include clock readings.

The desktop WGPU scene host checks complete script flows, submission cost, and memory use. GXM drawing, color, frame time, and resource reclamation are checked with the Vita target build on the device.

Optional `thread-profiling` uses a platform-provided thread CPU clock to record raw CPU and wall-clock samples, query overhead, and errors for VM slices, rendering submission, and presentation at the full presentation and submission boundary. The platform first checks whether the counter supports short-interval observation. Reports retain unavailable states and anomalous samples. It samples every 127th VM slice and every occurrence of the other two stages. Offline reports preserve sampling scope, and ordinary builds elide the observers.

A `profiling` build can enable exclusive wall-clock accounting for the calling thread. Each interval counts only toward the current innermost phase, with unscoped time and observation overhead reported separately. Phases spanning presentation boundaries split at those boundaries. Fixed-capacity stack overflow and ordering errors accompany samples. Version 1 frame reports append named nanosecond columns. Offline tools verify each row's total of phase, unassigned, and lost time. Driver call wall time includes waiting inside the call. The report retains the most recent 512 frames and the 64 earlier frames with the highest active time, in submission order. Samples made stale by label eviction leave the report. Compare the same profiling build with the probe disabled and enabled to measure added overhead.

Desktop sampling records `host_wait` from the time the event loop yields to the system until the next event iteration starts. Swapchain acquisition and display submission keep separate call timings.

Borrowed implementations are maintained as workspace crates. Their provenance, licenses, and required copyright notices live with the relevant crates. UI is from Masonry, text from Parley, audio mixing from Kira, and syntax trees from Rowan. Reel maintains the code under its current module boundaries. General-purpose algorithms favor pinned Rust dependencies such as Taffy, HarfRust, ICU, Symphonia, Lyon, and WGPU.

## Execution, waits, and scheduling

Compiler and VM share a bytecode model. Ordinary `main` starts after module initialization. The host verifies code identity, native signatures, ABI, capabilities, and supported instructions. Faults retain the creator's source location. Read-only leaf calculations from trusted registrations execute inside a VM slice, use regular argument preparation and return publication, and count toward the VM work allowance. Curve sampling and scalar math share calculation code with ordinary host entry points.

The compiler turns mutable instruction buffers into compact code and releases analysis data by module. Bytecode files, runtime, and snapshots use code-word offsets. Jumps, exception ranges, and source mappings all use that coordinate system.

Instructions compress into 32 KiB blocks. Verified programs share cold code and a bounded hot-page cache. The VM fetches instructions directly within the current page and decompresses on page changes. The residency allowance returns when all holders release a page. Loading validates per block. Snapshots retain code identity and execution positions.

The VM advances within instruction, internal work, allocation, and clock limits. It checks instruction, work, and allocation allowances incrementally. It checks the soft deadline on entry or resume, on host return, and after bounded execution batches. `BudgetYield` preserves the current position and intermediate state. Host calls yield values, faults, continuation state, or wait tickets. Long operations run in slices and commit their specified result when successful. Execution state retains side effects already made by user callbacks.

The GC's weak-reference phase walks a separate queue whose range for the current collection is fixed at the end of marking. The queue capacity counts against the heap budget before creating a weak reference. Collection reads and writes existing storage. New weak references enter the next collection. Cleared or unreachable weak references leave the queue. Liveness uses the same mark cutoff. Sweeping invalidates the object first, then directly releases its value blocks. Each block counts against the work allowance and returns its memory allowance after actual release.

Performance builds record work units for root scanning, marking, weak references, object sweeping, and reclamation by submission interval. Session timing supplies total GC time in the same interval.

Generators execute on demand within the caller's task. `yield` leaves a suspended frame's locals and fault context with the generator object. Advancing, closing, and snapshots use the same executor and GC. Unreachable generators release their state. Explicitly closing a generator runs cleanup it has already entered.

An explicit `await` provides a scheduling boundary. Even an already-complete object gives other tasks a chance to run. Host waits settle through stable identities and deliver at most once after matching session, owner, and generation. Waiters for a shared activity each hold a subscription. Cancelling one waiter releases its subscription, and the activity continues under its own ownership.

Property activities acquire write ownership at the final binding source. Creator assignment, manual scrolling, and explicit positioning can take over scroll position. Layout clamping and list anchor feedback are system updates. Automatic anchor compensation yields position control while the scroll activity holds the source. Range clamping continues to apply.

The main loop advances when there is input, activity, resource completion, GC, or retirement work. `game.configure(frame_rate: ...)` selects a target update rate for tweens, particles, transitions, and native control animations. It accepts 1–1000 Hz and defaults to automatic (`0`), which follows the host display rate or uses 60 Hz when the rate is unknown. Fixed-rate sample times align with the logical clock. A late update samples current time and skips elapsed sample times. `"uncapped"` samples continuous animation as soon as frame production is idle. Queued frames still follow shared backpressure. Explicit clocks and dialogue use separate deadlines, vertical sync comes from window settings, and stable scenes reuse the accepted frame. Before sleeping, the host acknowledges wake signals, handles their sources, and checks for remaining work. The Vita main thread keeps redraw requests as local state. After consuming them it sleeps to the activity deadline. New redraw requests made during rendering enter the next loop iteration before sleeping. I/O, media, display completion, and power events use retained cross-thread wake notifications. If a task cannot meet its minimum local budget, the host schedules the next slice using the reported requirement while retaining the loop's overall work boundary.

When native control animation and continuous story animation run together, they share the story animation's next sample time. If only control animation is running, that control's fixed cadence wakes the host. The actual animation step uses elapsed time between samples.

The host processes external media, localization, and resource read completions at the start of each advancement. VM slices and native reentry inside the iteration continue local scheduling. New external completions signal a wake for the next iteration. Hosts that use `SessionVm` directly call the corresponding `maintain_*` methods to process completions.

A clock update and its derived computations can span several host slices. When the script reaches a publication boundary and the derived batch completes, it returns to the host to allow publication of a complete frame. A pending redraw first records that stable projection, then the next iteration continues ready scripts. Activity deadlines, actual input, and resource completions drive timed sampling. Maintenance slices reuse the current time batch. Activities continue on the clock while scripts wait.

If a hard VM capacity limit prevents progress, the player completes a garbage collection and retries. If it still cannot proceed, it reports the source position and resource requirement and ends the run.

Session time uses a monotonic clock and freezes while the host is suspended. Stage animation, reading cadence, audio content position, and real time use their respective clocks. `std::time` reads real time. Continuous gameplay can update ordinary stage nodes through named actions and clock updates.

## Ownership, cancellation, and resource budgets

Sessions, tasks, nodes, scopes, and external requests have explicit identities. Copying a VM `Value` copies its handle. A host that retains a value across execution slices registers the corresponding GC root. Registers, native arguments, continuations, wait results, and fault references use one root and snapshot system.

A node's child block builds the children to attach during that invocation. `spawn` and `scope.spawn` need an ordinary task context. Put them after the child block and use an `owner` or scope to manage work lifetime.

`scope.wait()` suspends the task that owns the scope. Calling `finish(value)` from an input callback retires the scope body and supplies the result to the surrounding `scope` call. Cancellation clears waits through the same task retirement path.

Generational identities and occupancy bitmaps index root ranges. Each incremental GC scan unit reads one descriptor, one value, or one 64-slot occupancy word. It skips empty slots by block. After a range replacement it continues at the first value of the new generation. The bitmap reserves capacity alongside its descriptors and counts against the heap budget. GC slices read existing storage only.

Revoking an owner first closes new requests and business waits, then cancels tasks, clears VM roots, and retires external resources. The corresponding allowance returns after physical release. Owner slots can be reused once all recorded obligations end. GC handles unreachable script objects. Owners coordinate external device lifetimes.

Containers and buffers account for actual capacity. Growth reserves capacity for overlapping old and new storage before it happens. Owned data travels with its budget ticket. Final physical release returns the allowance. Shared aliases retain one allocation and ticket. Indivisible allocation and deallocation costs are measured separately.

Resource domains that share physical memory can join a budget group. Reservations and adjustments must satisfy both domain and group limits. Failure keeps existing accounting. Final release returns both allowances. An owned buffer can transfer atomically between domains of the same group. While checking the target limit, its original shared group ticket still counts once. Failure keeps the original ticket and data. The group peak records bytes held simultaneously across domains.

For reloadable images and textures, resource identity, version, dimensions, format, source, and coverage description are independent of the CPU payload. Uploads, saves, and other CPU readers hold payload read leases. Once the backend owns the same version, a reloadable payload with no readers can be reclaimed and its original allowance returned. Generated data and data without a reliable reload source retain their payloads. Ordinary stage images draw by resource identity and recording a frame does not extend a pixel Blob's lifetime.

After upload and CPU pixel release, the device cache can retain the same image identity. The identity and weak pixel-source description count against the mount's Metadata budget by actual capacity. Cache eviction releases references and allowance. The player looks up the image in the device cache with the existing origin index. Idle decoded pixels that have not been uploaded stay in a cache under the source resource budget and are admitted and reclaimed by byte count.

When backend reconstruction or a cache miss needs a reclaimed payload, the player uses existing Assets requests to reload the exact version asynchronously. Requests for the same resource coalesce. Version and description are checked before installing it under the original identity. The accepted frame remains visible during loading. On failure or cancellation, resources and presentation are preserved and the result is reported to the original source. Snapshots retain origins for reloadable resources. Other resources hold separate payload leases. Source conflict detection retains the original registration identity, and eviction and reload preserve the handle.

When a candidate frame lacks CPU pixels, the backend reports a bounded request identifying the candidate, device generation, and exact resource lease. This capacity counts toward the existing preparation budget. Requests deduplicate by resource identity and version. The player submits the requirement through existing asynchronous Assets requests, preserving the candidate in `Preparing` and keeping the last accepted frame. After completion it verifies the same candidate and device generation, restores the original resource, and notifies the presentation coordinator to continue the candidate. Cancellation, session switches, surface changes, and device reconstruction withdraw the associated request. Already submitted GPU work retires along its original completion signal. The GPU backend reports actual cache misses only. Assets manages reading, decoding, coalescing, cancellation, and errors. The resource itself stores its description and whether its pixels are resident or absent.

Background I/O, decode, and completion queues have explicit capacities. Before accepting a request, the system reserves a result slot. Rejection returns the original request and its ownership. If a consumer temporarily fills its queue, pending work stays queued and a release or completion notification wakes it. Stale results are released along their original ownership path.

Vita uses a unified C, newlib, and Rust process heap. The CRT starts with a 1 MiB cached MAIN arena and creates separate system mspaces and kernel blocks on demand. Once an additional arena is empty, it returns the entire block. A failed release retains the UID and charge. The first block remains available for small allocations. CPU arenas, GXM rings, USSE, MAIN texture and buffer storage, and firmware scheduling blocks share actual MAIN commitment accounting. A full page-aligned capacity including headers counts once and is returned after physical release succeeds. Before starting graphics, session, and media worker threads, the host determines capacity by adding remaining kernel MAIN space to managed commitments. It checks the SFO expansion allowance, loaded program, thread stacks, and SceLibc heap separately. Untracked SDK allocations may still cause kernel allocation failures later. The VM and resource domains retain their own admission checks. Shared verified code allowances held by multiple VMs do not accumulate in physical accounting. Physically contiguous MAIN uses a separate kernel report of remaining capacity. Video blocks retain both a media-local allowance and a physical ticket for the contiguous domain. NV12 imports share the original block. Reports keep ordinary and contiguous free space separate, without assuming the two cannot overlap.

Budgets separately cover the VM heap, CPU source and output, decode workspaces, GPU residency, and temporary targets. On Windows, Linux, and macOS, WGPU windows default to 1 GiB each for GPU resources and offscreen targets and 64 MiB for temporary rendering data. Image preparation stages and uploads up to 64 MiB of temporary data per step. The default limit for decoded CPU resources is 512 MiB. Budgets are consumed on demand. Sliced submission uses `Preparing` to wait to continue, and allocation pressure reclaims caches within the relevant ledger. Explicit budgets and Vita quotas retain their supplied values. Each ledger records the storage it actually owns. Measure process RSS, driver workspaces, and internal third-party decode workspaces separately. See [reel-core](../crates/reel-core/src/lib.rs) and the [VM](../crates/aside-vm/src/lib.rs).

Origin reuse uses weak leases and a budgeted identity index. On a hit, the implementation checks the full path, version, and kind. Retired resources cannot gain new leases. Released records are cleared in batches as the index grows. Capacity and overlapping storage during growth count toward Metadata. Under pressure, the index clears released records before deciding whether to fall back to scanning the source table. Closing the service releases the index.

Archive indexes use compact records and a shared UTF-8 path area. Entries borrow index storage. The `Metadata` ledger admits the actual capacities of the index, mount table, and parsing workspace. `AssetOptions.metadata_bytes` defaults to a 32 MiB limit. Mounting releases the parsing workspace. The index and mount table are released with the I/O worker. Decode workspace has a separate ledger.

## Stage, layout, and text

Each stage node has one logical parent. A constructor returns an unattached node. `add` and `stage.replace` commit attachment, `remove` retires a node, and `move` reorders a node under the same parent. Node identity carries callbacks, focus, activities, and resource references.

`layered_image` composes images by array position. The entire group, individual positions, and image properties can all be bound. Changing an expression keeps the image node at each unchanged position. Setting a position to `null` hides it temporarily. Shortening the array retires the trailing nodes. The constructor shares properties and defaults with `image`.

The `image_skin` of a visible control declares its artwork for each interaction state. Once the current frame is ready, the player uses spare prefetch capacity to prepare those paths. States sharing a source share the request. Inactive states are excluded from initial frame readiness. Fixed-size images use the existing viewport filter.

The native declaration for `list(items, key, build)` supplies the known element type of `items()` to inline `key(item)` and `build(row)` in the editor. `row.value` has the element type and `row.index` is int. Author annotations determine explicitly declared callback parameter types.

## Saving, restoration, and system data

Story saves store stable flow, wait, and return identities, persistent application objects, activities, the current interaction, and stage and media descriptors. Restoration uses current code definitions while retaining saved application values and alias relationships.

Host property validators and callbacks are rebuilt from the current type and view definitions.

Capture freezes session state and advances within object, edge, and byte allowances. It samples media playback descriptors at the start, retaining positions, queues, and pause state while real-time output continues. Input that needs to change session state fails the capture with `CaptureBusy` and preserves the original slot. Completed background saves publish atomically. A thumbnail and checkpoint publish together. Listing enumerates logical saves individually and opens the chosen committed generation. Resolution and file opening share one commit boundary. Open files keep read ownership of their previous generation, and thumbnail payloads load on demand.

Restoration first allocates identities, connects the graph, and rebuilds host descriptors in an isolated candidate. Once validated, the candidate replaces the current session. Ready restoration steps share the host time slice and yield when waiting for resources or after the slice expires. Code updates match current definitions by stable identity. Field type or resume-point contract conflicts report their exact location. The host recreates device handles, and the new session identity invalidates stale completion messages.

`persistent` stores application data separately, making it suitable for settings and unlock progress. Reads return plain data copies. Authors apply current system data at startup and after story restoration. Story slots and system data publish atomically and independently.

Save capture, candidate restoration, and result commit advance within a main-thread allowance. After dispatch to the storage thread, the host waits for its terminal event to wake it. Normal shutdown continues outstanding storage work and exits when it settles.

Vita storage publishes logical files using immutable data generations and commit records. Reads and enumeration use the same storage interface. A full commit reclaims older generations. An interrupted write keeps the last committed content.

Production story saves use a single logical format. This replaces the old execution snapshot's save, load, and format branches. The storage service still provides background encoding, thumbnails, and atomic publication.

Reading history is stored in pages. Capture shares pages within its budget. The live session takes its own copy before modifying a shared page. On-disk checkpoints encode history entries in their existing order.

A game can call `saves.track_history(true)` from its Root. The player attempts capture at actually presented dialogue waits and uses a fixed work allowance per capture. The in-memory window holds up to 64 positions and 2 MiB of logical state. The history menu queries and requests restoration by entry `group_id`. Clicking uses the same save-load candidate and session replacement flow, reconnects reading history through that entry, and discards later rollback points.

### Cross-version logical checkpoints

- Persistent application data uses checkable types, stable field identities, and pure data defaults. Classes and static protocol declarations provide constraints. ### Root, State, and application execution boundaries

The author interface expresses persistent data, flow identity, and ordinary game behavior. The compiler distinguishes interaction waits and flow returns. The engine handles candidate sessions, restoration injection, resource reconnection, and frame layout. New games and save loading use current views and application definitions. Loading cursors and device handles remain internal.

Normal return, failure, and cancellation follow existing native callback terminal handling. Capture records only the application continuation above this boundary. Current code builds main, view closures, and outer native context.
